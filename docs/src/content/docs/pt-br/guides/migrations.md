As suas entidades descrevem como o banco deve ficar; as migrations são os passos que levam um banco até lá. Cada migration é um arquivo TypeScript com uma função `up`, que aplica uma mudança, e uma função `down`, que a desfaz. A CLI escreve as migrations para você a partir das mudanças no modelo, e você pode editá-las ou escrever as suas.

As migrations funcionam com SQLite, PostgreSQL e MongoDB. O adapter em memória não guarda schema, então `migrate` não tem nada a fazer ali e `migration add` falha com `Migrations are not used with the memory adapter`.

Rode os comandos dentro do projeto com `bun run quickservice <comando>`. Os exemplos desta página usam um projeto SQLite com esta entidade:

```ts check title="entities/User.ts"
export type User = {
  /** @unique */
  email: string;
};
```

## `migration add`

`migration add <Nome>` compara as entidades com o snapshot da última migration e escreve a diferença:

```bash
bun run quickservice migration add Initial
```

```text
Created migrations/20261016223225_Initial.ts
```

O nome precisa estar em PascalCase (`^[A-Z][A-Za-z0-9]*$`) e ser único; o arquivo é `migrations/<YYYYMMDDHHmmss>_<Nome>.ts`. Agora adicione um campo a `User` em `entities/User.ts`:

```ts check
export type User = {
  /** @unique */
  email: string;
  age?: number;
};
```

O `build` (e portanto o `dev`) percebe a mudança:

```bash
bun run quickservice build
```

```text
Built 3 entities, 0 custom endpoints and 0 hooks.
Warning: Model has changes without a migration. Run "quickservice migration add <Name>"
```

(As três entidades são `User` e as embutidas `File` e `Media`.) Adicione uma migration para ela:

```bash
bun run quickservice migration add AddAge
```

```text
Created migrations/20261016223226_AddAge.ts
```

O arquivo gerado:

```ts check title="migrations/20261016223226_AddAge.ts"
// Generated by quickservice migration add. Review and edit as needed.
// ctx.repos reflects the latest model, not the model at the time of this migration.
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql("ALTER TABLE `{{default_schema}}users` ADD `age` real;");
}

export async function down(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("ALTER TABLE `{{default_schema}}users` DROP COLUMN `age`;");
}
```

- Comandos que podem perder dados (apagar uma tabela ou coluna, mudar o tipo de uma coluna) ganham o comentário `// WARNING: possible data loss`. Leia esses comandos antes de aplicar.
- No SQLite, `{{default_schema}}` representa o prefixo do [schema padrão](/pt-br/guides/configuration/). O `migrate` o substitui ao rodar, então uma mesma migration funciona com qualquer `DATABASE_SCHEMA`. No PostgreSQL, as tabelas do schema padrão ficam sem qualificação e o search path escolhe o schema.
- Um nome já usado, ou fora de PascalCase, falha:

```bash
bun run quickservice migration add AddAge
bun run quickservice migration add addAge
```

```text
A migration named AddAge already exists: 20261016223226_AddAge
Migration names must be PascalCase and match ^[A-Z][A-Za-z0-9]*$ (got "addAge")
```

### Snapshots

Ao lado de cada migration, `migration add` salva o modelo que ela produz em `migrations/meta/<id>.snapshot.json`. O próximo `migration add` compara com o snapshot mais recente no disco, não com o banco; por isso, faça commit dos snapshots junto com as migrations e não os edite.

### Migrations de dados

Quando nada mudou no modelo, `migration add` ainda cria um arquivo, com `up` e `down` vazios, para mudanças escritas à mão:

```bash
bun run quickservice migration add BackfillAges
```

```text
Created migrations/20261016223248_BackfillAges.ts
```

`up` e `down` recebem um `MigrationContext`:

- `ctx.sql` roda SQL na conexão da migration, como string ou como template marcado cujos valores viram parâmetros;
- `ctx.db` é a instância Drizzle dessa conexão;
- `ctx.repos` tem os repositórios do modelo atual. Eles seguem as entidades mais recentes, não o modelo da época da migration, então prefira `ctx.sql` em migrations que precisam continuar funcionando depois de mudanças futuras.

```ts check title="migrations/20261016223248_BackfillAges.ts"
import type { MigrationContext } from "@quickservice/core";

const DEFAULT_AGE = 18;

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql`update users set age = ${DEFAULT_AGE} where age is null`;
}

export async function down(ctx: MigrationContext): Promise<void> {
  await ctx.sql`update users set age = null where age = ${DEFAULT_AGE}`;
}
```

### Migrations automáticas no `dev`

Enquanto `quickservice dev` roda, uma mudança no modelo cria uma migration com um nome que a descreve, como `AddAgeToUsers`, `CreateOrder`, `RemoveAgeFromUsers` ou `UpdateModel` quando várias entidades mudam. Ele mostra `Created migrations/<id>.ts. Run "quickservice migrate" to apply it.`; nunca aplica a migration por você. Desligue isso com `migrations.autoInDev`; o `dev` passa a mostrar o aviso de mudanças pendentes:

```ts check title="quickservice.config.ts"
import { defineConfig, sqliteAdapter } from "@quickservice/core";

export default defineConfig({
  database: sqliteAdapter({ path: process.env.DATABASE_PATH! }),
  migrations: { autoInDev: false },
});
```

## `migrate`

`migrate` sem alvo aplica todas as migrations pendentes, na ordem dos ids:

```bash
bun run quickservice migrate
```

```text
Applied 20261016223225_Initial
Applied 20261016223226_AddAge
```

Rodar de novo não muda nada:

```text
Database is up to date (0 migrations applied)
```

As migrations aplicadas ficam registradas na tabela `__quickservice_migrations`. Cada uma roda na própria transação, junto com a sua linha de histórico: quando falha, as mudanças dela são desfeitas, o comando para com código de saída 1 e cita a migration, e as migrations anteriores continuam aplicadas.

### Migrando até um alvo

Passe um alvo, pelo nome ou pelo id completo, para avançar ou voltar até ele. Voltar roda o `down` de cada migration aplicada mais nova, da mais recente para a mais antiga:

```bash
bun run quickservice migrate Initial
```

```text
Reverted 20261016223226_AddAge
```

```bash
bun run quickservice migrate AddAge
```

```text
Applied 20261016223226_AddAge
```

O alvo `0` reverte tudo:

```bash
bun run quickservice migrate 0
```

```text
Reverted 20261016223226_AddAge
Reverted 20261016223225_Initial
```

Um alvo desconhecido, ou uma migration aplicada cujo arquivo sumiu, interrompe o comando:

```text
Unknown migration target: Nope
```

### `--force` em produção

Em produção (`NODE_ENV=production`, ou `production: true` na configuração), `migrate` se recusa a reverter qualquer coisa sem `--force`:

```bash
NODE_ENV=production bun run quickservice migrate Initial
```

```text
Reverting migrations in production requires --force (would revert: 20261016223226_AddAge)
```

```bash
NODE_ENV=production bun run quickservice migrate Initial --force
```

```text
Reverted 20261016223226_AddAge
```

## `migration list`

`migration list` mostra todas as migrations e o status de cada uma:

```bash
bun run quickservice migration list
```

```text
20261016223225_Initial  applied
20261016223226_AddAge  pending
```

| Status | Significado |
| --- | --- |
| `applied` | Está no histórico do banco. |
| `pending` | Está no disco, ainda não foi aplicada. |
| `missing` | Está no histórico, mas o arquivo sumiu. |
| `unknown` | Não foi possível acessar o banco; um aviso explica o motivo. |

Sem nenhuma migration, ele mostra `No migrations`.

## `migration remove`

`migration remove` apaga a migration mais nova e o snapshot dela, para você mudar o modelo e adicioná-la de novo. Ele só remove uma migration que não está aplicada:

```bash
bun run quickservice migration remove
```

```text
Migration 20261016223226_AddAge is applied. Revert it with "quickservice migrate Initial" first
```

Depois de `migrate Initial`:

```bash
bun run quickservice migration remove
```

```text
Removed migrations/20261016223226_AddAge.ts
Removed migrations/meta/20261016223226_AddAge.snapshot.json
```

Sem nada para remover, ele falha com `No migrations to remove`.

## `migration script`

`migration script [from] [to]` mostra o SQL entre dois pontos sem rodar nada, para revisão ou para um DBA aplicar. `from` tem padrão `0` (um banco vazio) e `to`, a migration mais nova; os dois aceitam um nome, um id completo ou `0`. De `Initial` até a mais nova:

```bash
bun run quickservice migration script Initial
```

```sql
-- 20261016223226_AddAge (up)
ALTER TABLE `users` ADD `age` real;
insert into __quickservice_migrations (id, name, applied_at) values ('20261016223226_AddAge', 'AddAge', cast(strftime('%s', 'now') as integer) * 1000);
```

Quando `to` vem antes de `from`, o script traz o SQL de `down`, da mais nova para a mais antiga:

```bash
bun run quickservice migration script AddAge Initial
```

```sql
-- 20261016223226_AddAge (down)
ALTER TABLE `users` DROP COLUMN `age`;
delete from __quickservice_migrations where id = '20261016223226_AddAge';
```

Os valores dos templates marcados aparecem no próprio SQL. Para a migration `BackfillAges` acima:

```sql
-- 20261016223248_BackfillAges (up)
update users set age = 18 where age is null;
insert into __quickservice_migrations (id, name, applied_at) values ('20261016223248_BackfillAges', 'BackfillAges', cast(strftime('%s', 'now') as integer) * 1000);
```

O SQL é coletado rodando cada migration com um `ctx.sql` que registra os comandos. Código que usa `ctx.db` ou `ctx.repos` não pode ser registrado, então aparece como `-- custom code in <id>, not scriptable`.

`--output <arquivo>` grava o script em um arquivo e não mostra nada:

```bash
bun run quickservice migration script --output schema.sql
```

## Renomeações

As migrations geradas nunca adivinham renomeações. Renomear um campo ou uma entidade vira uma remoção seguida de uma adição, o que perde os dados. Renomear `age` para `years` gera:

```ts check title="migrations/20261016223301_RenameAge.ts"
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("ALTER TABLE `{{default_schema}}users` DROP COLUMN `age`;");
  await ctx.sql("ALTER TABLE `{{default_schema}}users` ADD `years` real;");
}

export async function down(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("ALTER TABLE `{{default_schema}}users` DROP COLUMN `years`;");
  await ctx.sql("ALTER TABLE `{{default_schema}}users` ADD `age` real;");
}
```

Para manter os dados, troque os dois corpos por uma renomeação:

```ts check
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql("ALTER TABLE `{{default_schema}}users` RENAME COLUMN `age` TO `years`;");
}

export async function down(ctx: MigrationContext): Promise<void> {
  await ctx.sql("ALTER TABLE `{{default_schema}}users` RENAME COLUMN `years` TO `age`;");
}
```

O snapshot já descreve o novo modelo, então o próximo `migration add` parte dele. Uma renomeação é detectada: quando uma tabela de junção muda de nome (por exemplo, com um novo `@joinTable`) mas continua ligando os mesmos campos, a migration renomeia a tabela e mantém as linhas.

## MongoDB

No MongoDB os mesmos comandos funcionam, com estas diferenças:

- As migrations geradas criam e apagam índices (de `@unique`, `@index` e afins); não há tabelas para criar.
- `ctx` é um `MongoMigrationContext`: `ctx.db()` é o banco nativo do schema padrão, `ctx.db("<schema>")` o de outro schema, `ctx.client` o `MongoClient` e `ctx.repos` os repositórios.
- O histórico fica na coleção `_migrations` do banco padrão.
- As migrations rodam sem transações, porque mudanças de índice não podem rodar dentro de uma; `migrate` mostra `Warning: MongoDB migrations run without transactions: index changes cannot run inside one`.
- Remover ou renomear uma entidade nunca apaga a coleção dela. O `up` gerado traz `// TODO: data in collection <name> is kept; drop it here if intended` no lugar.
- `migration script` mostra comandos do `mongosh`, como `db.users.createIndex(...)`, e código próprio como `// custom code in <id>, not scriptable`.

Uma migration de dados escrita à mão no MongoDB:

```ts check
import type { MongoMigrationContext } from "@quickservice/core";

export async function up(ctx: MongoMigrationContext): Promise<void> {
  await ctx.db().collection("users").updateMany({ age: null }, { $set: { age: 18 } });
}

export async function down(ctx: MongoMigrationContext): Promise<void> {
  await ctx.db().collection("users").updateMany({ age: 18 }, { $set: { age: null } });
}
```
