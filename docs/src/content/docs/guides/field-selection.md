Three layers decide which fields a response carries:

1. **The entity** hides fields with [`@hidden`](/reference/tags/#hidden) and limits list and read responses with [`@fields`](/reference/tags/#fields).
2. **The client** narrows list and read responses further with `?fields=` and `?exclude=`.
3. **A custom endpoint** shapes its own result with the endpoint tags [`@fields`](/reference/tags/#fields-1) and [`@exclude`](/reference/tags/#exclude).

All of them use the same path syntax: field names separated by commas, with dots for nested properties (`name,address.city`). A path through an array of objects applies to every item (`orders.total`), and keeping a path keeps everything below it.

The examples on this page use this entity:

```ts check title="entities/User.ts"
/** @fields:list id,name,email */
export type User = {
  name: string;
  email: string;
  /** @hidden */
  passwordHash: string;
  /** @hidden:list */
  bio?: string;
  address?: {
    city: string;
    /** @hidden */
    zip?: string;
  };
};
```

## Fields that are never returned

`@hidden` removes a field from **every** response: list, read, and also the responses of create, replace and update. Clients can still write it. It works on nested properties too, like `address.zip` above.

```bash
curl -X POST localhost:3000/users -d '{"name":"Ana","email":"ana@example.com","passwordHash":"s3cret","bio":"Hi!","address":{"city":"Rio","zip":"20000"}}'
```

```json
{
  "name": "Ana",
  "email": "ana@example.com",
  "bio": "Hi!",
  "address": { "city": "Rio" },
  "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
  "createdAt": "2026-10-16T22:25:35.305Z",
  "updatedAt": "2026-10-16T22:25:35.305Z"
}
```

Repositories leave hidden fields out as well, which is why the generated `User` type marks them optional (an excerpt of `.generated/types.ts`):

```ts check title=".generated/types.ts"

```

When your code needs a hidden value, pass `includeHidden: true` to `findById`, `findOne` or `list`. This endpoint checks a password against the stored hash. It assumes `passwordHash` holds a hash made with `Bun.password.hash`, for example by a hook on create, rather than the placeholder sent above:

```ts check title="endpoints/sessions/post.ts"
import { HttpError, type Endpoint } from "@quickservicets/core";

type Login = { email: string; password: string };

/** @summary Check a password */
const handler: Endpoint<Login, { id: string; name: string }> = async (repos, req) => {
  const { email, password } = await req.json();
  const user = await repos.users.findOne([{ field: "email", op: "eq", value: email }], { includeHidden: true });
  if (!user || !(await Bun.password.verify(password, user.passwordHash ?? ""))) {
    throw new HttpError(401, "Wrong email or password");
  }
  return { id: user.id, name: user.name };
};

export default handler;
```

```bash
curl -X POST localhost:3000/sessions -d '{"email":"ana@example.com","password":"s3cret"}'
```

```json
{ "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f", "name": "Ana" }
```

## Fields hidden on list or read

`@hidden:list` hides a field only in the list route (`GET /users`), and `@hidden:read` only in the read route (`GET /users/:id`). Write responses still include it. Here `bio` is too long for lists, but the read route shows it:

```bash
curl localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f
```

```json
{
  "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
  "createdAt": "2026-10-16T22:25:35.305Z",
  "updatedAt": "2026-10-16T22:25:35.305Z",
  "name": "Ana",
  "email": "ana@example.com",
  "bio": "Hi!",
  "address": { "city": "Rio" }
}
```

## The fields an entity exposes

The entity tag `@fields` lists the only paths the list and read routes return. `@fields:list` applies it to the list route, `@fields:read` to the read route, and a plain `@fields` to both. Paths hidden for that route are still removed, and `id` is only returned when you list it.

With `@fields:list id,name,email`, lists are compact while the read route above keeps every field that is not hidden:

```bash
curl localhost:3000/users
```

```json
{
  "data": [{ "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f", "name": "Ana", "email": "ana@example.com" }],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

Listing a path in `@fields` that is hidden for the same route stops the build:

```text
entities/Post.ts: entity Post exposes "body" in @fields but it is hidden on list
```

The list route also accepts filters and sorts only on fields it exposes, so clients cannot probe fields they cannot see:

```bash
curl -g "localhost:3000/users?where[bio][eq]=Hi!"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "where[bio][eq]", "message": "Field \"bio\" cannot be filtered" }]
  }
}
```

```bash
curl "localhost:3000/users?sort=bio"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "sort", "message": "Field \"bio\" cannot be sorted" }]
  }
}
```

## Choosing fields in a request

The list and read routes take two query parameters, described in the [HTTP query parameters reference](/reference/http/):

- `fields`: the paths to keep.
- `exclude`: the paths to remove.

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?fields=name,address.city"
```

```json
{ "name": "Ana", "address": { "city": "Rio" } }
```

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?exclude=bio,createdAt,updatedAt"
```

```json
{
  "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
  "name": "Ana",
  "email": "ana@example.com",
  "address": { "city": "Rio" }
}
```

When both are given, `fields` applies first and `exclude` then removes paths from that selection:

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?fields=name,address&exclude=address.city"
```

```json
{ "name": "Ana", "address": {} }
```

Clients can only choose among the paths the route exposes. Selecting a hidden or not exposed path, excluding a path outside `fields`, or sending an empty list fails with 400:

```bash
curl "localhost:3000/users?fields=passwordHash"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "fields", "message": "Unknown field: passwordHash" }]
  }
}
```

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?fields=name&exclude=email"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "exclude", "message": "Field is not selected: email" }]
  }
}
```

```bash
curl "localhost:3000/users?fields="
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "fields", "message": "Must list at least one field" }]
  }
}
```

`?fields=` and `?exclude=` do not restrict filters: `?where[name][eq]=Ana&fields=email` filters by `name` and returns only `email`.

## Custom endpoints

A custom endpoint shapes its result with one of two endpoint tags: `@fields <paths>` keeps paths, `@exclude <paths>` removes them. Using both on one endpoint stops the build. The projection applies to each item of `data` when the result is `{ data: [...] }`, to each item of an array, and to the result itself otherwise; `Response` objects and empty results are left alone. It runs before post-hooks, so they see the projected data.

On an endpoint of its own, the paths are applied as written, and paths missing from the result are ignored:

```ts check title="endpoints/reports/signups/get.ts"
/** @exclude internalNote */
export default () => [
  { day: "2026-10-01", signups: 12, internalNote: "campaign A" },
  { day: "2026-10-02", signups: 9, internalNote: "campaign B" },
];
```

```bash
curl localhost:3000/reports/signups
```

```json
[
  { "day": "2026-10-01", "signups": 12 },
  { "day": "2026-10-02", "signups": 9 }
]
```

On an endpoint that overrides a generated list or read route, the tag **replaces** the entity's `@fields` and `@hidden:list`/`@hidden:read` rules for that route, and the build checks its paths against the entity. `@hidden` fields stay out, because the repository never returns them:

```ts check title="endpoints/users/get.ts"
import type { Endpoint } from "@quickservicets/core";

/** @exclude address.zip */
const handler: Endpoint = (repos) => repos.users.query().orderBy((user) => user.name).page({ limit: 20, offset: 0 });

export default handler;
```

```bash
curl localhost:3000/users
```

```json
{
  "data": [
    {
      "name": "Ana",
      "email": "ana@example.com",
      "bio": "Hi!",
      "address": { "city": "Rio" },
      "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
      "createdAt": "2026-10-16T22:25:35.305Z",
      "updatedAt": "2026-10-16T22:25:35.305Z"
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

An override without either tag keeps the entity's rules for its route. Custom endpoints ignore `?fields=` and `?exclude=`, which work only on generated routes.

## In the API docs

The OpenAPI document follows these rules. When a route exposes fewer fields than the full record, its response uses a reduced schema, `UserListItem` for the list route or `UserRead` for the read route, and the `fields` and `exclude` parameters list the paths clients can pick.
