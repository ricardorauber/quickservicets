A feature is a piece of a service that you turn on with a key in the config, like `greeting: {}`. The framework's own features (the natives) and the features you write in your project use the same contract: a definition with typed options, and fields that add entities, endpoints, hooks, jobs, tags, folders, commands, startup code, routes, middleware, request properties, OpenAPI changes and build steps. A project feature lives in `features/<key>/index.ts`, and one with the key of a native replaces that native.

This guide builds one small feature, `greeting`, that uses every extension point:

```text
my-api/
├── features/
│   └── greeting/
│       ├── index.ts           # the definition
│       ├── commands.ts        # quickservice greeting hello
│       ├── middleware.ts
│       ├── request.ts         # req.greeter
│       ├── entities/Greeting.ts
│       ├── endpoints/greetings/random/get.ts
│       ├── hooks/stamp.ts
│       └── jobs/count.ts
├── greetings/
│   └── formal.ts              # a folder the feature declares
├── entities/Post.ts
└── quickservice.config.ts
```

## `defineFeature`

`features/greeting/index.ts` default-exports `defineFeature(...)` with the key of its folder:

```ts check title="features/greeting/index.ts"
import { addOperation, defineFeature, duration, object, oneOf, string } from "@quickservice/core";
import { readFileSync } from "node:fs";
import { hello } from "./commands.ts";
import { poweredBy } from "./middleware.ts";
import { greeterFor } from "./request.ts";

const options = object({
  text: string().default("Hello").describe("How greetings start."),
  style: oneOf(["plain", "loud"]).default("plain"),
  retention: duration().default("30d"),
});

export default defineFeature({
  key: "greeting",
  options,
  docs: { summary: "Greets people." },
  entities: "./entities",
  endpoints: "./endpoints",
  hooks: "./hooks",
  jobs: "./jobs",
  tags: {
    greeting: {
      on: ["entity", "endpoint"],
      options: ["text", "style"],
      description: "Sets the greeting of one entity or route.",
      example: '/** @greeting text="Good day" */',
    },
  },
  folders: {
    greetings: { dir: "greetings", check: (value) => typeof value === "string" || "must default-export a string", description: "Greetings by name." },
  },
  watch: ["content/greetings.md"],
  commands: [hello],
  middleware: [poweredBy],
  request: { greeter: greeterFor },
  setup(ctx) {
    const greetings = ctx.folders.greetings ?? new Map();
    ctx.app.route("GET", "/greetings/today", () => ({ text: `${ctx.options.text}!`, known: [...greetings.keys()] }));
    ctx.app.route("GET", "/greetings/static/[...rest]", (_repos, req) => ({ file: req.params.rest }));
    let timer: ReturnType<typeof setInterval> | undefined;
    ctx.app.onStart(() => {
      timer = setInterval(() => ctx.logger.info({ message: "still greeting" }), 60_000);
    });
    ctx.app.onShutdown(() => ctx.logger.info({ message: "stopping greetings" }));
    ctx.app.onStop(() => clearInterval(timer));
    ctx.logger.info({ message: "greetings built", list: readFileSync(ctx.generated("greetings.json"), "utf8") });
  },
  openapi(doc) {
    addOperation(doc, "get", "/greetings/today", { summary: "Today's greeting", responses: { "200": { description: "The greeting" } } });
  },
  async build(ctx) {
    await ctx.cached(["greetings"], async () => {
      await ctx.write("greetings.json", JSON.stringify((ctx.folders.greetings ?? []).map((file) => file.name)));
    });
  },
});
```

The config turns it on with its key. `quickservice build` types the key with the feature's options, in `.generated/types.ts`:

```ts check title="quickservice.config.ts"
import { defineConfig, memoryAdapter } from "@quickservice/core";

export default defineConfig({
  database: memoryAdapter(),
  greeting: { text: "Hi" },
});
```

A feature is off until its key is set (`greeting: {}`, or `true`), or until `QS_GREETING_ENABLED=true` is set; `greeting: false` or `QS_GREETING_ENABLED=false` turns it off. `enabledByDefault: true` makes it on without a key.

### Options

`options` is an `object({...})` schema, written with the same builders as the config's `env` key. The build checks the config's values against it, the [environment](/guides/environment/) sets any option (`QS_GREETING_TEXT=Hey`), and the feature's code reads the resolved, typed values in `ctx.options`, or anywhere with `greeting.options()`.

### `requires`, `after` and `enables`

A feature can depend on other features, by key:

```ts check
import { defineFeature } from "@quickservice/core";

export default defineFeature({
  key: "newsletter",
  // Fails the build unless `greeting` is enabled, with this hint.
  requires: [{ name: "greeting", hint: "newsletters start with a greeting" }],
  // Runs after `audit` when `audit` is enabled, without needing it.
  after: ["audit"],
  // Turns `greeting` on with its default options when the config has no key for it.
  enables: ["greeting"],
});
```

Enabled features are ordered after the features they require, follow or enable; every extension point below runs in that order.

## Contributions

### Entities

`entities: "./entities"` adds the entity files of `features/greeting/entities/` to the project's model, parsed with the project's rules. They get routes, types, docs and migrations like the project's own entities:

```ts check title="features/greeting/entities/Greeting.ts"
export type Greeting = { name: string; text: string };
```

`entities` may also be a list of `entityModel(...)` objects, or a function of the project's models and the feature's options that returns models, for entities derived from the project's.

### Endpoints, hooks and jobs

`endpoints`, `hooks` and `jobs` are folders scanned with the project's rules. A feature's job is named `<key>/<path>`, here `greeting/count`.

```ts check title="features/greeting/endpoints/greetings/random/get.ts"
import type { Endpoint } from "@quickservice/core";

/** @summary A greeting for you */
const handler: Endpoint = (_repos, req) => ({ text: req.greeter.greet("you") });

export default handler;
```

```ts check title="features/greeting/hooks/stamp.ts"
import { definePostHook } from "@quickservice/core";
import greeting from "../index.ts";

export default definePostHook((data, _repos, req) => ({ ...(data as object), greeting: greeting.optionsFor(req).text }));
```

```ts check title="features/greeting/jobs/count.ts"
import { job } from "@quickservice/core";

export default job({ every: "1h" }, async ({ log }) => {
  log.info("greetings counted");
});
```

### Tags

`tags` adds JSDoc tags written with the names of the feature's options, so one entity, field or route can set them, or turn the feature off with `@greeting off`. The tag wins over the config and the environment for its target:

```ts check title="entities/Post.ts"
/**
 * @greeting text="Good day" style=loud
 * @stamp
 */
export type Post = { title: string };
```

The feature reads the options of a target with `greeting.optionsFor(...)`: an entity key or model, a field (`{ entity, field }`), an endpoint (`{ method, path }`) or a request, as the `stamp` hook above does. The result has `on`: `true` with the tag, `false` with `@greeting off`, and undefined without it.

Two fields of a tag definition make tags shorter. `shorthand: "text"` lets the first value be written bare, so `@greeting "Good day" style=loud` equals `@greeting text="Good day" style=loud`; giving the shorthand option twice fails the build. `scope: "<path>"` points the tag at a nested `object()` of the options: with `scope: "rateLimit"`, `@limit by=user` sets `rateLimit.by`, and `optionsFor` merges the tag's values into that object only, keeping its other keys and every other option as the config and the environment set them. `@limit off` on a scope with an `enabled` option also sets its `enabled` to false for that target.

### Folders

`folders` gives the project a convention folder. The build scans `greetings/**/*.ts` in the project and in the feature's folder, checks each default export, and hands them to the feature as `ctx.folders.greetings`, a map by file name:

```ts check title="greetings/formal.ts"
export default "Good day";
```

Other enabled features can ship files for the folder too, in the same folder inside their own (`features/<key>/greetings/`), like a feature shipping listener files for the `events/` folder of the `events` native. A project file replaces a feature's file of the same name, with an `Override:` line; two features shipping the same name fail the build. A folder declared with `featurePrefix: true` names a shipped file `<key>/<path>`, after the key of the feature that ships it, as feature jobs are named: the `queues` native's folder names `features/billing/queues/close.ts` `billing/close`, and a project file `queues/billing/close.ts` replaces it. `quickservice dev` rebuilds when a folder or a `watch` path changes.

### Commands

`commands` adds `quickservice <name>` commands with typed flags; `quickservice help` lists them under the feature's key:

```ts check title="features/greeting/commands.ts"
import { boolean, defineCommand, object } from "@quickservice/core";

export const hello = defineCommand({
  name: "greeting hello",
  usage: "quickservice greeting hello <name> [--loud]",
  description: "Prints a greeting.",
  args: [{ name: "name", required: true }],
  flags: object({ loud: boolean().default(false) }),
  run({ args, flags, options, output }) {
    const text = `${String(options.text)}, ${args.name}!`;
    output.log(flags.loud ? text.toUpperCase() : text);
  },
});
```

```bash
bun run quickservice greeting hello Ana --loud
```

```text
HI, ANA!
```

`ctx.connect()` gives a command the project's repositories.

## Runtime extension points

### Setup and lifecycle

`setup(ctx)` runs in each server process before the database connects, in feature order. Through `ctx.app` it registers `onStart` (after the app is created, before the server listens, with working repositories), `onShutdown` (when a shutdown signal arrives) and `onStop` (after the listener closed and jobs drained) callbacks, as the definition above does. A failing or slow `setup` or `onStart` stops the service with exit code 1; `lifecycle.startTimeout` and `lifecycle.stopTimeout` bound each call.

### Hooks and feature APIs

A `hook()` option lets the project run code around one of the feature's steps, written as a function or a list of functions in the config. Name it `before<Step>` (it may return a changed value, or throw to cancel the step), `after<Step>` (it observes the result) or `on<Event>` (it observes something that happened); other names fail `defineFeature`. Hooks resolve to a list and have no environment variable. `runBeforeHooks(list, value, ctx)` passes each hook's returned value to the next and rejects when one throws; `runAfterHooks(list, value, ctx)` logs a failing hook as `feature.hook.failed` and keeps going. Skip both when the list is empty, so an unused hook costs nothing.

`api(ctx)` returns the feature's public API, built once per process after its `setup`. Another feature that lists it in `requires` or `after` reaches it with `ctx.feature(key)`, typed by augmenting `FeatureApis`, and `ctx.addHook(name, fn)` appends a hook after the config's:

```ts check
import { defineFeature, hook, object, runBeforeHooks, type FeatureHook } from "@quickservice/core";

type Note = { text: string };

export interface NotesApi {
  addHook(name: "beforeSave", fn: FeatureHook<Note>): void;
  save(note: Note): Promise<Note>;
}

declare module "@quickservice/core" {
  interface FeatureApis {
    notes: NotesApi;
  }
}

export const notes = defineFeature({
  key: "notes",
  options: object({ beforeSave: hook<Note>().describe("Runs before a note is saved.") }),
  api: (ctx) => ({
    addHook: ctx.addHook,
    save: async (note: Note) => (ctx.options.beforeSave.length === 0 ? note : runBeforeHooks(ctx.options.beforeSave, note, undefined)),
  }),
});

export const shouting = defineFeature({
  key: "shouting",
  requires: ["notes"],
  setup(ctx) {
    ctx.feature("notes").addHook("beforeSave", (note) => ({ text: note.text.toUpperCase() }));
  },
});
```

### Routes

`ctx.app.route(method, path, handler)` adds a route at runtime, with `[param]` segments and a trailing `[...rest]` segment that receives the rest of the path. An endpoint file with the same method and path wins over it. `ctx.app.configureServer({ clientIp })` replaces how `req.ip` is computed from the request and its peer address; two features giving the same server setting fail at startup.

### Middleware

`middleware` (or `ctx.app.use` in setup, or the config's `middleware` key) runs code before routing (`request`), around every handler (`handler`) or on every error (`error`):

```ts check title="features/greeting/middleware.ts"
import type { Middleware } from "@quickservice/core";

export const poweredBy: Middleware = {
  stage: "request",
  async run(_ctx, next) {
    const response = await next();
    response.headers.set("x-greeting", "on");
    return response;
  },
};
```

A `handler` middleware may set the typed `req.user`, `req.tenant` and `req.flags`. A `request` middleware that refuses a request can call `ctx.errorResponse(error)` to get the response the `error` stage gives an `HttpError`, and keep adding headers to it on the way out; an `HttpError` created with `{ headers }` carries those headers in its response.

### Request properties

`request` adds a property to every request, computed on first read and kept for the request. Declare its type in `RequestExtensions`:

```ts check title="features/greeting/request.ts"
import type { ServiceRequest } from "@quickservice/core";

export interface Greeter {
  greet(name: string): string;
}

declare module "@quickservice/core" {
  interface RequestExtensions {
    greeter: Greeter;
  }
}

export const greeterFor = (req: ServiceRequest): Greeter => ({ greet: (name) => `Hello, ${name} (request ${req.id})` });
```

### OpenAPI

`openapi(doc)` changes the generated document at build time; `addOperation`, `addSchema`, `addSecurityScheme` and `requireSecurity` help, as the definition above shows. The project's own `docs.openapi` runs after every feature's.

### Build steps

`build(ctx)` writes files into `.generated/greeting/` during `quickservice build`; `ctx.cached` skips the work when its inputs did not change, and `ctx.generated(...)` in setup reads the result.

## Replacing a native

A project feature with the key of a native replaces it: the config keeps `<key>: {…}`, and the build prints `Override: features/<key> replaces the <key> native`. To start from the native's code instead of a blank file, eject it:

```bash
bun run quickservice eject history                         # the whole native into features/history/
bun run quickservice eject history --file jobs/prune.ts    # one file, into jobs/history/prune.ts
```

The copied files import the framework from `@quickservice/core`. Deleting `features/<key>/` goes back to the native.

## The public API only

Files under `features/` import the framework only from `@quickservice/core` (and `@quickservice/core/testing`); the build fails naming a file that imports a path inside the package, so a feature keeps working when the framework's internals change. The natives follow the same rule inside the framework.

## Testing a feature

`startTestService` from `@quickservice/cli/testing` builds a project from a few files and starts it in the test process, on the memory database and without a port:

```ts check title="tests/greeting.test.ts"
import { expect, test } from "bun:test";
import { readFileSync } from "node:fs";
import { join } from "node:path";
import { startTestService } from "@quickservice/cli/testing";

const root = join(import.meta.dir, "..");
const files = Object.fromEntries(
  [...new Bun.Glob("{quickservice.config.ts,features/**/*.ts,greetings/**/*.ts,entities/**/*.ts}").scanSync(root)].map((path) => [path, readFileSync(join(root, path), "utf8")]),
);

test("today's greeting", async () => {
  const service = await startTestService({ files, env: { QS_GREETING_TEXT: "Hey" } });
  try {
    const response = await service.fetch("/greetings/today");
    expect(await response.json()).toEqual({ text: "Hey!", known: ["formal"] });
  } finally {
    await service.stop();
  }
});
```

`stop()` runs the shutdown sequence and fails when a timer the feature started is still running after `onStop`.
