# Benchmark API contract

Every stack in this study implements the same HTTP API on the same PostgreSQL schema. The reference is the QuickService service in [`quickservice/`](quickservice/): this document describes what it actually returns, and [`conformance/conformance.ts`](conformance/conformance.ts) checks it against any base URL. A stack is valid only when the conformance test passes against it.

## 1. Rules for implementers

- **Location.** `benchmarks/stacks/<name>/` with a `Dockerfile`; the build context is that folder. Use a lowercase name (`express`, `fastify`, `bun`, `fastapi`, `go`, `rust`, `dotnet`, `java`, `php`, `cpp`). `bun benchmarks/run.ts <name>` builds and measures it.
- **Production setup.** Build and run the way the framework's own documentation recommends for production: release/optimized builds, production mode flags (`NODE_ENV=production`, `ASPNETCORE_ENVIRONMENT=Production`, `GIN_MODE=release`, ...), the server and worker model the framework recommends (for example uvicorn workers for FastAPI, PHP-FPM or a production app server for PHP). Size worker counts for **2 CPUs**; the container gets `--cpus=2 --memory=1g`. Multi-stage images are encouraged; pin every base image to an exact version.
- **Port.** Listen on `0.0.0.0:8080` (the `PORT` variable is also set to `8080`).
- **Database.** PostgreSQL 17, reached through the variables below. Use the framework's idiomatic driver or ORM with a connection pool of exactly **`DB_POOL_SIZE` = 10 connections** per container (QuickService uses Bun.SQL's default pool of 10). If the stack runs several processes, the total across processes must still be 10. Do not create, migrate or alter tables: `run.ts` creates the schema from [`schema/schema.sql`](schema/schema.sql) and seeds it before the service starts.

  | Variable | Value in the run |
  | --- | --- |
  | `DATABASE_URL` | `postgres://bench:bench@qsbench-postgres:5432/bench` |
  | `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` | `qsbench-postgres`, `5432`, `bench`, `bench`, `bench` |
  | `DB_POOL_SIZE` | `10` |
  | `UPLOAD_DIR` | `/data/uploads` (a Docker volume, writable by any user) |
  | `PORT` | `8080` |

- **No caching.** Every request reads from and writes to PostgreSQL. No response caches, no in-process record caches, no HTTP caching headers that let k6 skip requests. Prepared-statement caches and the connection pool are fine.
- **Same work.** Validate everything this contract validates, with the same messages. Sort, filter and page in SQL (PostgreSQL's ordering and collation decide the order, see [Sorting](#sorting)). Any query strategy is allowed (joins, `IN` lists, aggregates in SQL): the goal is what an experienced developer would write by hand for this API.
- **Logging.** QuickService writes one JSON line per request to stdout by default and that is part of what is measured. Other stacks keep their framework's production default; do not add debug logging.
- **Startup.** `GET /health` must answer `200 {"ok":true}` once the service can serve requests. Startup time is measured from `docker start` to the first `200` on `/health`, so do the work you need (pool warm-up, JIT) before or after as your framework normally does, but do not delay the listener artificially.
- **Graceful stop.** Exit on `SIGTERM` within 10 seconds (`docker stop -t 10`).

## 2. General conventions

- **Content type.** Every JSON response has `Content-Type: application/json` (a `; charset=utf-8` parameter is accepted). Clients send JSON bodies with `Content-Type: application/json`; behavior with other content types on JSON routes is not tested.
- **Field order** inside JSON objects does not matter. Order inside arrays does (list pages, `members`).
- **Ids** are UUID version 7 ([RFC 9562](https://www.rfc-editor.org/rfc/rfc9562)) strings in lowercase canonical form (`01a154e8-7f9f-74a5-8c4d-c902c2e9968f`), generated by the service when a record is created. The seed uses UUID v7 too. A path id that matches no record (including strings that are not UUIDs, such as `does-not-exist`) is a `404`, never a `400`.
- **Timestamps** (`createdAt`, `updatedAt`) are generated by the service, stored in `timestamp with time zone` columns, and serialized in UTC with exactly three fractional digits: `2026-10-19T16:04:45.600Z` (JavaScript's `Date.prototype.toISOString`). Truncate to milliseconds before storing, so that what is stored and what is returned are equal. On create, `createdAt` equals `updatedAt`. Every successful `PATCH` sets `updatedAt` to the current time, even when the body is `{}`.
- **Numbers.** `age` is serialized as a JSON integer (`30`, not `30.0`; parsers compare numerically, but prefer integers). `averageAge` is a full-precision double, not rounded. `size` is an integer.
- **Nulls.** An optional field without a value is present with `null` (`"age": null`), never omitted.
- **204** responses have no body.
- **Extra headers** (such as QuickService's `x-request-id`) are allowed and ignored.

## 3. Records

### User

```json
{
  "id": "019b76da-a800-7f45-bd8a-93424b9ff367",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z",
  "email": "user00000@example.com",
  "name": "User 0",
  "role": "member",
  "age": 56
}
```

| Field | Type | Rules |
| --- | --- | --- |
| `email` | string | required; matches `^[^\s@]+@[^\s@]+\.[^\s@]+$`; unique, **case-sensitive** (`A@x.io` and `a@x.io` can coexist) |
| `name` | string | required; 1 to 100 characters (UTF-16 code units, as JavaScript's `length`) |
| `role` | `"member"` \| `"admin"` | defaults to `"member"` on create; case-sensitive; cannot be `null` |
| `age` | integer or `null` | optional; integer from 0 to 150 |

### Organization

```json
{
  "id": "019c168f-0a58-75b3-a3ac-9c1e1ff82d10",
  "createdAt": "2026-02-01T00:16:39.000Z",
  "updatedAt": "2026-02-01T00:16:39.000Z",
  "name": "Organization 999",
  "slug": "org-0999",
  "members": ["019b7771-bbc8-776f-a360-0360d48ede19", "019b76e3-7200-7026-af53-d57f461fbfe8"]
}
```

`members` is a reference array: the ids of `User` records, in stored order (the `position` column of `organizations__members`, ascending), never `null` (an organization without members has `[]`). With `populate=members` each id is replaced by the full user record, in the same order (see [Populate](#populate)).

### Media

```json
{
  "id": "01a154e9-751c-719f-ab60-621cab3194d6",
  "createdAt": "2026-10-19T16:05:48.444Z",
  "updatedAt": "2026-10-19T16:05:48.444Z",
  "filename": "upload.png",
  "mimeType": "image/png",
  "size": 51288,
  "storage": "default",
  "url": "/media/01a154e9-751c-719f-ab60-621cab3194d6/file"
}
```

`storage` is always `"default"`. `url` is always the relative path `/media/<id>/file`, computed on every read and never stored. The `storage_key` column is never returned.

## 4. Endpoints

| Method and path | Success | Errors |
| --- | --- | --- |
| `GET /health` | `200 {"ok":true}` | |
| `GET /users` | `200` list page of users | `400` invalid query |
| `GET /users/{id}` | `200` user | `400` invalid `fields`; `404 User not found` |
| `POST /users` | `201` the created user | `400` invalid JSON or body; `409` email taken |
| `PATCH /users/{id}` | `200` the updated user | `400`; `404 User not found`; `409` email taken |
| `DELETE /users/{id}` | `204`, no body | `404 User not found` |
| `GET /organizations` | `200` list page of organizations | `400` invalid query |
| `GET /organizations/{id}` | `200` organization | `400`; `404 Organization not found` |
| `GET /organizations/{orgId}/stats` | `200` stats | `404 Organization not found` |
| `POST /media` | `201` the media record | `400`, `413`, `415`, see [Uploads](#7-uploads) |
| `GET /media/{id}` | `200` media record | `404 Media not found` |
| `GET /media/{id}/file` | `200` the stored bytes | `404 Media not found` |
| any other path | | `404 {"error":{"code":"NOT_FOUND","message":"Route not found"}}` |

Responses for a wrong method on a known path (QuickService answers `405 Method not allowed` with an `allow` header) are not tested.

### `GET /users/{id}` and `GET /organizations/{id}`

Return the record. Both take `fields` (and `GET /organizations/{id}` takes `populate`) with the same meaning as on the list routes. Other query parameters on read routes are ignored.

### `POST /users`

Body: `{ "email", "name", "role"?, "age"? }`, validated as in [Validation](#6-validation-of-json-bodies). Responds `201` with the full record: generated `id`, `createdAt` = `updatedAt` = now, `role` defaulted to `"member"`, `age` defaulted to `null`. A taken email answers:

```json
// 409
{"error":{"code":"CONFLICT","message":"Value already exists","details":[{"field":"email","message":"Value already exists"}]}}
```

Detect the conflict from the unique index (`users_email_uq`, SQLSTATE `23505`), not with a check-then-insert that races.

### `PATCH /users/{id}`

Body: any subset of `{ "email", "name", "role", "age" }`. Only the given fields change; `updatedAt` always moves to now. `age: null` clears the age; `null` for `email`, `name` or `role` is a validation error. The body is validated first: an invalid body is a `400` even when the id does not exist, and a valid body (including `{}`) on a missing id is `404 User not found`. A taken email is the same `409` as on create. Responds `200` with the full updated record.

### `DELETE /users/{id}`

Deletes the user and removes it from every organization's `members`. In the same transaction, every organization that listed the user gets `updatedAt` = now, and the remaining members keep their relative order (renumbering `position` is optional). Responds `204` with no body; a missing id is `404 User not found`. The junction rows cascade through the foreign key, but the `updatedAt` change of the owning organizations must be done by the service.

### `GET /organizations/{orgId}/stats`

```json
{"members":10,"admins":1,"averageAge":51.77777777777778}
```

- `members`: number of member users;
- `admins`: members whose `role` is `admin`;
- `averageAge`: arithmetic mean of the members' non-null ages, as a double; `null` when no member has an age (or there are no members).

An unknown `orgId` is `404 {"error":{"code":"NOT_FOUND","message":"Organization not found"}}`. QuickService computes this with `repos.organizations.findById` and a fluent `repos.users.where(...).aggregate(...)` query; other stacks may compute it in SQL.

### `GET /media/{id}/file`

Streams the stored bytes with these headers:

```http
Content-Type: image/png                       (the record's mimeType)
Content-Length: 51288                         (the record's size)
Content-Disposition: inline; filename="upload.png"
```

In the filename, quotes, backslashes and control characters (`"`, `\`, U+0000 to U+001F) are removed.

## 5. List queries

`GET /users` and `GET /organizations` answer with a page:

```json
{"data":[ ... ],"total":10000,"limit":20,"offset":0}
```

`total` counts every record that matches the filters (not just the page). `limit` and `offset` echo the values used. An offset past the end returns `"data": []` with the real `total`.

### Parameters

| Parameter | Meaning | Default |
| --- | --- | --- |
| `limit` | integer from 1 to 100 | 20 |
| `offset` | integer of at least 0 | 0 |
| `sort` | comma-separated field names, `-` prefix for descending | `-createdAt` |
| `where[<field>][<op>]` | filter; several are combined with AND | none |
| `fields` | comma-separated field names to return | every field |
| `populate` | `members` (organizations only) | none |

Any other parameter is `400` with `Unknown parameter` for that name (for example `foo`, `where`, `where[age]`), and a parameter given twice is `400` with `Parameter is repeated`.

### Sorting

- Sortable fields. Users: `id`, `createdAt`, `updatedAt`, `email`, `name`, `role`, `age`. Organizations: `id`, `createdAt`, `updatedAt`, `name`, `slug` (not `members`).
- **Tie-breaker**: `id` descending is always appended, unless `id` is already in the list. The default order is therefore `created_at DESC, id DESC`, and `sort=-age,email` means `ORDER BY age DESC, email ASC, id DESC`.
- **Nulls** follow PostgreSQL's default: last in ascending order, first in descending order. Do not add `NULLS FIRST/LAST` clauses.
- **Collation**: the database default (`en_US.utf8` in the `postgres:17.11-alpine` image, which compares by code point). Sort in SQL, not in application code.
- A field listed twice is `400` with `Field "<name>" is listed more than once` (not tested).

### Filters

The operators every stack must support (more are allowed):

| Collection | Field | Operators |
| --- | --- | --- |
| users | `role` | `eq`, `ne`, `in` (comma-separated, up to 100 values) |
| users | `age` | `eq`, `ne`, `gt`, `gte`, `lt`, `lte` |
| users | `email` | `eq` |
| organizations | `slug` | `eq` |

- Values are parsed by field type: `age` values must be numbers (`30`, `30.5`), otherwise `Must be a number`; `role` values must be `member` or `admin`, otherwise `Must be one of: member, admin`.
- `ne` follows SQL semantics: `where[age][ne]=30` does not match rows whose `age` is `null`.
- An operator the field does not support (for example `where[role][gt]`): `Operator "gt" is not allowed for this field`. A name that is not an operator at all (`where[age][between]`): `Unknown operator "between"`. A field that does not exist: `Field "<name>" cannot be filtered`.

### Field selection

`fields` lists top-level field names, including `id`, `createdAt`, `updatedAt` and, on organizations, `members`. Each item of `data` (or the single record on read routes) then has exactly those fields. An unknown name is `400` with `Unknown field: <name>` on the `fields` parameter; an empty value is `Must list at least one field`. Nested paths such as `members.email` (QuickService supports them with `populate`) are optional and not tested.

### Populate

`populate=members` on `GET /organizations` and `GET /organizations/{id}` replaces the member ids with full user records (the same shape as `GET /users/{id}`), in `position` order. Ids whose user no longer exists are left out. Any other value is:

```json
// 400
{"error":{"code":"VALIDATION_ERROR","message":"Cannot populate: email","details":[{"field":"populate","message":"Cannot populate: email"}]}}
```

`GET /users?populate=<anything>` fails the same way (users have no references). QuickService loads the members of a whole page with one query; other stacks should avoid N+1 queries too.

### Query errors

All problems found in the query are reported together, one entry per problem, under `"message": "Invalid query"`:

```json
// GET /users?limit=0&offset=-1&foo=2 → 400
{"error":{"code":"VALIDATION_ERROR","message":"Invalid query","details":[
  {"field":"foo","message":"Unknown parameter"},
  {"field":"limit","message":"Must be an integer from 1 to 100"},
  {"field":"offset","message":"Must be an integer of at least 0"}]}}
```

| Request | `field` | `message` |
| --- | --- | --- |
| `limit=0`, `limit=101`, `limit=abc`, `limit=2.5` | `limit` | `Must be an integer from 1 to 100` |
| `offset=-1` | `offset` | `Must be an integer of at least 0` |
| `foo=1` | `foo` | `Unknown parameter` |
| `limit=1&limit=2` | `limit` | `Parameter is repeated` |
| `sort=bogus` | `sort` | `Field "bogus" cannot be sorted` |
| `sort=members` (organizations) | `sort` | `Field "members" cannot be sorted` |
| `where[age][gte]=abc` | `where[age][gte]` | `Must be a number` |
| `where[role][eq]=owner` | `where[role][eq]` | `Must be one of: member, admin` |
| `where[role][gt]=admin` | `where[role][gt]` | `Operator "gt" is not allowed for this field` |
| `where[nope][eq]=1` | `where[nope][eq]` | `Field "nope" cannot be filtered` |
| `fields=nope` | `fields` | `Unknown field: nope` |

The conformance test compares `details` without regard to order; QuickService lists unknown parameters first, then the others in the order it checks them.

## 6. Validation of JSON bodies

An invalid JSON document (including an empty body) is:

```json
// 400
{"error":{"code":"VALIDATION_ERROR","message":"Invalid JSON body"}}
```

Valid JSON that is not an object (`[]`, `null`, `"text"`, `42`) is:

```json
// 400
{"error":{"code":"VALIDATION_ERROR","message":"Invalid body","details":[{"field":"","message":"Body must be a JSON object"}]}}
```

Otherwise every field is checked and every problem is reported together, at most one message per field:

```json
// POST /users {"email":"not-an-email","role":"owner","age":30.5,"extra":1} → 400
{"error":{"code":"VALIDATION_ERROR","message":"Invalid body","details":[
  {"field":"email","message":"Must be a valid email"},
  {"field":"name","message":"Is required"},
  {"field":"role","message":"Must be one of: member, admin"},
  {"field":"age","message":"Must be an integer"},
  {"field":"extra","message":"Unknown field"}]}}
```

Per field, the first failing rule wins, in this order:

| Rule | Message | Applies to |
| --- | --- | --- |
| missing on `POST` | `Is required` | `email`, `name` |
| `null` | `Cannot be null` | `email`, `name`, `role` (`age: null` is valid) |
| wrong JSON type | `Must be a string` / `Must be a number` | strings / `age` |
| not an integer | `Must be an integer` | `age` (`30.0` is an integer) |
| length | `Must be at least 1 characters` / `Must be at most 100 characters` | `name` |
| format | `Must be a valid email` | `email` |
| range | `Must be at least 0` / `Must be at most 150` | `age` |
| enum | `Must be one of: member, admin` | `role` (a non-string is also this message) |
| system field | `Field is read-only` | `id`, `createdAt`, `updatedAt` |
| anything else | `Unknown field` | any other key |

QuickService lists the details in entity field order (`email`, `name`, `role`, `age`), then read-only and unknown keys in body order; the conformance test does not check the order. Validation errors are reported before the unique-email check, so a body with both problems is a `400`.

## 7. Uploads

`POST /media` takes `multipart/form-data` with the file in a part named `file`. The checks run in this order, and the first one that fails decides the response:

1. **Not multipart** (for example a JSON body): `415 {"error":{"code":"UNSUPPORTED_MEDIA_TYPE","message":"Must be multipart/form-data"}}`.
2. **No `file` part** (or a `file` part that is a plain field, not a file): `400 Invalid body` with `{"field":"file","message":"Is required"}`, whatever the other parts are.
3. **Type detection** from the content (magic bytes), compared with the part's declared `Content-Type` (its essence: parameters dropped, lowercased; the file name plays no part):

   | Content | Declared type | Type used |
   | --- | --- | --- |
   | recognized format | the same type | the detected type |
   | recognized format | missing or `application/octet-stream` | the detected type |
   | recognized format | any other type | none: `415` (below) |
   | not recognized | anything | the declared type |

   ```json
   // PNG bytes declared image/gif → 415
   {"error":{"code":"UNSUPPORTED_MEDIA_TYPE","message":"File content does not match its type","details":[{"field":"file","message":"Detected image/png, declared image/gif"}]}}
   ```

   Stacks must recognize at least PNG (`89 50 4E 47 0D 0A 1A 0A`), JPEG (`FF D8 FF`), GIF (`GIF87a`/`GIF89a`), WebP (`RIFF....WEBP`) and PDF (`%PDF-`). QuickService also recognizes ZIP, DOCX, XLSX, MP4, WebM and MP3; supporting them is optional.
4. **Size**: larger than 1 MiB (1,048,576 bytes; exactly 1 MiB is accepted): `413 {"error":{"code":"PAYLOAD_TOO_LARGE","message":"File too large"}}` (no `details`).
5. **Accepted types**: the type from step 3 must be `image/png` or `image/jpeg`, otherwise `400 Invalid body` with `{"field":"file","message":"File type not allowed"}`. Note that unrecognized bytes declared as `image/png` pass (QuickService stores them as `image/png`).
6. **Other parts.** A part named `id`, `createdAt`, `updatedAt`, `filename`, `mimeType`, `size`, `storage` or `url`: `400 Invalid body` with `Field is read-only` for that name. Any other name: `Unknown field`.
7. **Store, then insert.** Generate the record id (UUID v7) and an object id (another UUID v7), write the bytes to `${UPLOAD_DIR}/media/<id>/<objectId><ext>` (creating the folders), where `<ext>` is the lowercased extension of the file name including the dot (empty when the name has none), then insert the row with `storage_key` = `media/<id>/<objectId><ext>` and `storage` = `default`. If the insert fails, delete the written file. No `fsync` is required. During the load, `run.ts` deletes stored files that are a few seconds old to bound disk use, so never read them back in a request other than `GET /media/{id}/file`.

`filename` is the part's file name reduced to its base name (`../../etc/evil.png` becomes `evil.png`), with control characters removed and cut to 255 characters. `size` is the byte length and `mimeType` the type from step 4.

The response is `201` with the media record (`url` = `/media/<id>/file`). The k6 `upload` scenario sends a 51,288-byte PNG ([`load/fixtures/upload.png`](load/fixtures/upload.png)) declared as `image/png`.

## 8. Errors

Every error body is `{"error":{"code","message","details"?}}`. `details`, when present, is an array of `{"field","message"}`. The code depends only on the status:

| Status | Code |
| --- | --- |
| 400 | `VALIDATION_ERROR` |
| 404 | `NOT_FOUND` |
| 409 | `CONFLICT` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 500 | `INTERNAL_ERROR` (message `Internal server error`, no stack traces in production) |

Not-found messages: `User not found`, `Organization not found`, `Media not found`, `Route not found`. A `404` has no `details`.

## 9. Database schema

[`schema/schema.sql`](schema/schema.sql) is the exact DDL the QuickService migration creates (generated with `quickservice migration script`; regenerate with `bun benchmarks/schema/generate.ts`). `run.ts` drops and recreates the `public` schema, applies it, and loads the seed before each stack. Stacks must use these tables and columns as they are:

```sql
CREATE TABLE "users" (
	"id" text PRIMARY KEY NOT NULL,
	"created_at" timestamp with time zone NOT NULL,
	"updated_at" timestamp with time zone NOT NULL,
	"email" text NOT NULL,
	"name" text NOT NULL,
	"role" text NOT NULL,
	"age" double precision,
	CONSTRAINT "users_role_check" CHECK ("users"."role" in ('member', 'admin'))
);
CREATE TABLE "organizations" (
	"id" text PRIMARY KEY NOT NULL,
	"created_at" timestamp with time zone NOT NULL,
	"updated_at" timestamp with time zone NOT NULL,
	"name" text NOT NULL,
	"slug" text NOT NULL
);
-- The reference array Organization.members: one row per member, ordered by position.
CREATE TABLE "organizations__members" (
	"owner_id" text NOT NULL,
	"target_id" text NOT NULL,
	"position" integer NOT NULL,
	CONSTRAINT "organizations__members_pk" PRIMARY KEY("owner_id","target_id")
);
ALTER TABLE "organizations__members" ADD CONSTRAINT "organizations__members_owner_id_organizations_id_fk" FOREIGN KEY ("owner_id") REFERENCES "organizations"("id") ON DELETE cascade ON UPDATE no action;
ALTER TABLE "organizations__members" ADD CONSTRAINT "organizations__members_target_id_users_id_fk" FOREIGN KEY ("target_id") REFERENCES "users"("id") ON DELETE cascade ON UPDATE no action;
CREATE TABLE "media" (
	"id" text PRIMARY KEY NOT NULL,
	"created_at" timestamp with time zone NOT NULL,
	"updated_at" timestamp with time zone NOT NULL,
	"filename" text NOT NULL,
	"mime_type" text NOT NULL,
	"size" double precision NOT NULL,
	"storage" text NOT NULL,
	"storage_key" text NOT NULL
);
-- "files" (the built-in File entity, same columns as media) exists but no endpoint uses it.
CREATE INDEX "users_created_at_idx" ON "users" USING btree ("created_at");
CREATE UNIQUE INDEX "users_email_uq" ON "users" USING btree ("email");
CREATE INDEX "organizations_created_at_idx" ON "organizations" USING btree ("created_at");
CREATE UNIQUE INDEX "organizations_slug_uq" ON "organizations" USING btree ("slug");
CREATE INDEX "organizations__members_target_idx" ON "organizations__members" USING btree ("target_id");
CREATE INDEX "media_created_at_idx" ON "media" USING btree ("created_at");
```

Notes:

- Ids are `text`, not `uuid`: bind them as strings. An id that is not a UUID simply matches nothing.
- `age` and `size` are `double precision`: read them as numbers and serialize integral values as JSON integers.
- `role` is checked by the database too, but the service must validate it first and answer `400`.
- There are no indexes on `role` or `age`: the filtered list scans `users`, for every stack alike. Do not add indexes.
- The seed ([`seed/`](seed/)) has 10,000 users (created one second apart from `2026-01-01T00:00:00Z`, about 20 % admins, about 10 % without age) and 1,000 organizations (one second apart from `2026-02-01T00:00:00Z`, slugs `org-0000` to `org-0999`) with 10 members each, positions 0 to 9; every user belongs to exactly one organization. It is regenerated identically on every run and reloaded before each scenario.
