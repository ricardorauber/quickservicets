O banco em memória esquece tudo a cada reinício. Nesta página você leva o projeto para o PostgreSQL, cria suas tabelas com uma **migration** e aumenta a profundidade do populate para o endpoint da próxima parte.

## Por que migrations

Um banco SQL precisa de tabelas antes de guardar registros. Uma migration é um arquivo TypeScript em `migrations/` que leva o banco de uma versão do seu modelo para a seguinte. O quickservice a escreve para você comparando suas entidades com a última migration, e você a revisa antes de aplicá-la.

## Inicie o PostgreSQL

Qualquer servidor PostgreSQL serve. Com Docker:

```bash
docker run -d --name identity-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
```

## Aponte o projeto para ele

Primeiro, pare o servidor de desenvolvimento (`Ctrl+C`). Depois, coloque a URL de conexão no `.env` do projeto, que o Bun carrega em todo comando:

```bash
DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres
```

E troque o adapter em `quickservice.config.ts`:

```ts check
import { defineConfig, postgresAdapter } from "@quickservice/core";

export default defineConfig({
  database: postgresAdapter({ url: process.env.DATABASE_URL! }),
});
```

:::note
O `.env` está no `.gitignore` do projeto, então as credenciais ficam fora do git.
:::

## Crie a primeira migration

```bash
bun run quickservice migration add Initial
```

```text
Created migrations/20261016222539_Initial.ts
```

O nome é em PascalCase: uma letra maiúscula, seguida de letras e dígitos. O comando também grava um snapshot do modelo em `migrations/meta/`, com o qual a próxima migration se compara. Abra o arquivo para revisá-lo. Aqui está ele, resumido:

```ts check title="migrations/20261016222539_Initial.ts"
// Generated by quickservice migration add. Review and edit as needed.
// ctx.repos reflects the latest model, not the model at the time of this migration.
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql("CREATE TABLE \"memberships\" (\n\t\"id\" text PRIMARY KEY NOT NULL,\n\t\"created_at\" timestamp with time zone NOT NULL,\n\t\"updated_at\" timestamp with time zone NOT NULL,\n\t\"organization\" text NOT NULL,\n\t\"user\" text NOT NULL,\n\t\"active\" boolean NOT NULL\n);");
  await ctx.sql("CREATE TABLE \"permissions\" (\n\t\"id\" text PRIMARY KEY NOT NULL,\n\t\"created_at\" timestamp with time zone NOT NULL,\n\t\"updated_at\" timestamp with time zone NOT NULL,\n\t\"module\" text NOT NULL,\n\t\"action\" text NOT NULL,\n\tCONSTRAINT \"permissions_action_check\" CHECK (\"permissions\".\"action\" in ('manage', 'view'))\n);");
  // … as outras tabelas, chaves estrangeiras e índices
}

export async function down(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("DROP TABLE \"memberships\" CASCADE;");
  // … as outras tabelas
}
```

A migration cria:

- Uma tabela por entidade, mais `files` e `media` para as entidades de arquivo embutidas.
- Uma tabela de junção para cada array de referências de mão única: `memberships__profiles`, `organizations__modules`, `profiles__permissions` e `teams__profiles`.
- Uma tabela de junção para a relação N-N entre times e usuários: `teams__users`.

Os lados derivados não ganham nada: `users` não tem coluna `memberships`, porque cada vínculo guarda seu `user`. Campos enum viram colunas de texto com um `CHECK` nos seus valores, como `action` acima.

## Aplique a migration

Primeiro, liste as migrations:

```bash
bun run quickservice migration list
```

```text
20261016222539_Initial  pending
```

Aplique todas as migrations pendentes:

```bash
bun run quickservice migrate
```

```text
Applied 20261016222539_Initial
```

Agora a lista a mostra como aplicada, e rodar `migrate` de novo não muda nada:

```bash
bun run quickservice migration list
bun run quickservice migrate
```

```text
20261016222539_Initial  applied
Database is up to date (0 migrations applied)
```

## Rode no PostgreSQL

Inicie o servidor de desenvolvimento de novo:

```bash
bun run dev
```

As rotas são as mesmas de antes. Só o armazenamento mudou, e agora os registros sobrevivem aos reinícios:

```bash
curl -X POST localhost:3000/modules -d '{"slug":"billing","active":true}'
```

```json
{
  "id": "01a1…16ec",
  "createdAt": "2026-10-16T22:25:51.375Z",
  "updatedAt": "2026-10-16T22:25:51.375Z",
  "slug": "billing",
  "active": true
}
```

## Permita caminhos de populate mais profundos

A próxima parte verifica as permissões de um usuário carregando de uma vez os perfis de cada vínculo, suas permissões e o módulo de cada permissão: `profiles.permissions.module`. Esse caminho tem três segmentos, e o populate permite dois por padrão. Depois de recriar alguns registros (módulo, permissão, perfil, organização, usuário e vínculo), experimente:

```bash
curl "localhost:3000/memberships/<membership-id>?populate=profiles.permissions.module"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Populate depth exceeds 2",
    "details": [{ "field": "populate", "message": "Populate depth exceeds 2" }]
  }
}
```

Aumente o limite com `populate.maxDepth`. Este é o `quickservice.config.ts` final:

```ts check title="quickservice.config.ts"
import { defineConfig, postgresAdapter } from "@quickservice/core";

export default defineConfig({
  database: postgresAdapter({ url: process.env.DATABASE_URL! }),
  // "profiles.permissions.module" has three segments.
  populate: { maxDepth: 3 },
});
```

O servidor de desenvolvimento reinicia quando a configuração muda. A mesma requisição agora devolve a cadeia inteira:

```bash
curl "localhost:3000/memberships/<membership-id>?populate=profiles.permissions.module"
```

```json
{

  "createdAt": "2026-10-16T22:25:27.291Z",
  "updatedAt": "2026-10-16T22:25:27.291Z",
```

## Quando o modelo mudar depois

Enquanto o `bun run dev` roda no PostgreSQL, ele cria uma migration para você sempre que uma mudança de entidade precisa de uma, dá a ela um nome conforme a mudança e imprime `Created migrations/<id>_<Name>.ts. Run "quickservice migrate" to apply it.` Revise o arquivo e depois rode `migrate`.

- Para escrever migrations só à mão, defina `migrations: { autoInDev: false }` na configuração e rode `migration add <Name>` você mesmo.
- `bun run quickservice migration remove` apaga a migration mais recente enquanto ela ainda não foi aplicada.
- `bun run quickservice migrate <nome ou id>` avança ou volta até essa migration, e `migrate 0` reverte todas.
