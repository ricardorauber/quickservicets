# Jobs

> Run code on a schedule or on demand, with every run recorded in the database, timeouts, retries and clean shutdowns.

A job is code that runs on its own: every five minutes, every night at 03:00 in São Paulo, or once at a given date. You write each job as a file in `jobs/`, and the server runs it at its scheduled times, once across all instances, recording every run in the database with its outcome, its returned value and its log lines. The same job can also run on demand, from the CLI or from an endpoint.

## Declaring a job

Each `.ts` file under `jobs/` default-exports a `job(schedule, run, options?)` call. The job's name is the file's path under `jobs/` without the extension, so this file declares `cleanup/expired-sessions`:

```ts title="jobs/cleanup/expired-sessions.ts"
import { job } from "@quickservicets/core";

export default job("*/5 * * * *", async ({ repos, log }) => {
  const expired = await repos.sessions.where((s) => s.expiresAt.lt(new Date())).toArray();
  for (const session of expired) await repos.sessions.delete(session.id);
  log.info("Expired sessions deleted", { deleted: expired.length });
  return { deleted: expired.length };
});
```

Subfolders group related jobs (`jobs/billing/close-invoices.ts` is `billing/close-invoices`), and test files (`*.test.ts`, `*.spec.ts`) are left out. The build checks every file and writes the job registry to `.generated/jobs.ts`.

The first job also adds the built-in `JobRun` entity to the model, where the runs are recorded. Its table (or collection, on MongoDB) is called `job-runs`, so the build asks for a migration once:

## Schedules

The first argument says when the job runs:

| Schedule | Example | Runs |
| --- | --- | --- |
| Cron, 5 fields | `"*/5 * * * *"` | every 5 minutes (minute, hour, day of month, month, day of week) |
| Cron, 6 fields | `"0 30 9 * * 1-5"` | at 09:30:00 on weekdays (seconds first) |
| Preset | `"@daily"` | at midnight; also `@yearly`, `@monthly`, `@weekly` and `@hourly` |
| Interval | `{ every: "10m" }` | every 10 minutes; units `s`, `m`, `h`, `d`, at least `1s` |
| Single date | `{ at: "2026-12-01T09:00:00Z" }` | once, at that instant |

Cron fields take ranges (`1-5`), steps (`*/15`) and lists (`0,30`).

Intervals are aligned to the clock, not to when the server started: `{ every: "15m" }` runs at :00, :15, :30 and :45 UTC, and `{ every: "10s" }` at :00, :10, :20 and so on. So restarts and replicas agree on the run times.

A single date runs once. When that instant has already passed when the server starts, the job does not run. More generally, run times are only computed forward from now: runs missed while the service was down are skipped, never made up.

### Time zones

Cron schedules are evaluated in the job's `timeZone` option, else in `jobs.timeZone` from the config, which defaults to `UTC`. This job closes the previous month's open invoices at 00:05 on the first day of each month, São Paulo time:

```ts title="jobs/billing/close-invoices.ts"
import { job } from "@quickservicets/core";

export default job(
  "5 0 1 * *",
  async ({ repos, log }) => {
    const open = await repos.invoices.where((i) => i.status.eq("open").and(i.dueAt.lt(new Date()))).toArray();
    for (const invoice of open) await repos.invoices.update(invoice.id, { status: "closed" });
    log.info("Invoices closed", { closed: open.length });
    return { closed: open.length };
  },
  { timeZone: "America/Sao_Paulo" },
);
```

On days when the clocks change, a wall time that does not exist (02:30 on a spring-forward day in New York) runs at the first instant after the gap, 03:00, and a wall time that happens twice (on the fall-back day) runs once, at its first occurrence. Intervals and single dates are instants, so the time zone does not affect them.

## The job context

The closure receives one argument, `ctx`:

| Key | What it is |
| --- | --- |
| `repos` | The typed repositories, the same ones endpoints and hooks get. |
| `files` | The configured file storages, as `files.default` and one key per storage. |
| `signal` | An `AbortSignal`, aborted when the run times out or the server shuts down. |
| `log` | `info`, `warn` and `error`, each taking a message and optional fields. |
| `run` | The run being executed: `id`, `job`, `scheduledAt`, `attempt` (from 1) and `trigger` (`schedule`, `manual` or `code`). |
| `http` | The outgoing [HTTP client](/guides/http-client/), sending the run's id as `x-request-id`. |

Whatever the closure returns becomes the run's `result`, stored as JSON. A closure that throws, or returns a rejected promise, makes the run `failed`.

`ctx.log` lines go to the service log with the `job` and `runId` fields, and into the run record's `logs`:

```json
{"level":"info","timestamp":"2026-10-19T15:31:48.494Z","message":"Expired sessions deleted","deleted":3,"job":"cleanup/expired-sessions","runId":"01a154ca-5487-75b8-b0bb-1b5d40d1157b"}
```

Each run also writes a `job.started` and a `job.finished` entry, the latter with `status` and `durationMs`:

```json
{"level":"info","timestamp":"2026-10-19T15:31:48.495Z","message":"job.finished","job":"cleanup/expired-sessions","runId":"01a154ca-5487-75b8-b0bb-1b5d40d1157b","status":"success","durationMs":7}
```

## Options

The third argument holds the job's options. Each one is optional and overrides the matching default from the `jobs` config:

| Option | Default | What it does |
| --- | --- | --- |
| `timeZone` | `jobs.timeZone`, `"UTC"` | The IANA time zone cron schedules are evaluated in. |
| `overlap` | `"skip"` | What a run does while the previous one is still running: [`skip` or `parallel`](#overlapping-runs). |
| `timeout` | `jobs.timeout`, `"5m"` | The longest a run may last ([timeouts](#timeouts)). |
| `retries` | `jobs.retries`, `0` | How many times a failed run is retried ([retries](#retries)). |
| `retryDelay` | `jobs.retryDelay`, `"30s"` | The delay before the first retry, doubled for each next one. |
| `retention` | `jobs.retention`, `"30d"` | How long the job's run records are kept ([retention](#retention)). |

Durations are a whole number and a unit: `30s`, `10m`, `2h` or `30d`.

The `jobs` key of `quickservicets.config.ts` sets the defaults for every job, plus the settings that belong to the whole service:

```ts title="quickservicets.config.ts"
import { defineConfig, sqliteAdapter } from "@quickservicets/core";

export default defineConfig({
  database: sqliteAdapter({ path: process.env.DATABASE_PATH! }),
  jobs: {
    timeZone: "America/Sao_Paulo",
    timeout: "10m",
    retries: 1,
    retryDelay: "1m",
    retention: "14d",
    // How long a shutdown waits for running jobs.
    shutdownGrace: "30s",
    // The largest stored result and the most stored log lines per run.
    limits: { result: "64KB", logLines: 500 },
  },
});
```

`jobs.enabled` (default `true`) turns the scheduler off for this instance, and `JOBS_ENABLED=false` in the environment overrides it. Invalid values stop the CLI and the server with the key, for example `Invalid jobs.timeout: expected a duration like 30s, 10m or 30d, got "soon"`. Every key is in the [Configuration reference](/reference/config/).

## Run records

Every run, scheduled or not, is one `JobRun` record:

| Field | What it holds |
| --- | --- |
| `job` | The job name. |
| `trigger` | `schedule`, `manual` (from `job run`) or `code` (from `req.jobs.run`). |
| `scheduledAt` | The run time this run belongs to; for runs on demand, the moment they were asked for. |
| `attempt` | `1`, then `2`, `3`... for [retries](#retries) of the same run time. |
| `status` | See below. |
| `startedAt`, `finishedAt`, `durationMs` | When the run started and ended, and how long it took. |
| `heartbeatAt` | The last sign of life of a long run ([abandoned runs](#abandoned-runs)). |
| `result` | The returned value, as JSON. |
| `error` | `{ message, stack }` for runs that did not succeed; no `stack` in production. |
| `logs` | The `ctx.log` lines: `{ level, message, at, fields }`. |

| Status | Meaning |
| --- | --- |
| `running` | The run is in progress. |
| `success` | The closure returned. |
| `failed` | The closure threw. |
| `timedOut` | The run lasted longer than its `timeout`. |
| `skipped` | The run did not start because the previous one was still running. |
| `abandoned` | The instance running it stopped sending heartbeats, for example because it crashed. |
| `interrupted` | The server shut down before the run finished. |

Records stay small. Beyond `jobs.limits.logLines` (500), a run keeps the first 499 lines and a last `<n> more lines omitted`. A result larger than `jobs.limits.result` (64 KB) is not stored, and a warning line says so: `Result larger than 64KB was not stored`. A value that cannot be turned into JSON gets `Result is not JSON-serializable` instead.

`job runs` lists the latest runs of a job (20 unless you pass `--limit`), newest first:

```bash
bun run quickservicets job runs cleanup/expired-sessions --limit 3
```

```text
ATTEMPT  TRIGGER   STATUS   STARTED                   DURATION
1        schedule  success  2026-10-19T15:45:00.021Z  7ms
1        manual    success  2026-10-19T15:36:59.613Z  8ms
```

In code, `repos.jobRuns` reads the records. It has the read methods only (`findById`, `findOne`, `list`, `where`, `query`, `any`, `all`, `none`, `count`): the framework writes the runs, so `repos.jobRuns.create(...)` does not type-check. Run records have no HTTP routes and no place in the API docs; an endpoint like this one exposes what you choose:

```ts title="endpoints/job-failures/get.ts"
import type { Endpoint } from "@quickservicets/core";
import type { JobRun } from "../../.generated/types.ts";

/** @summary Runs that did not succeed in the last 24 hours */
const handler: Endpoint<unknown, JobRun[]> = (repos) => {
  const since = new Date(Date.now() - 24 * 60 * 60 * 1000);
  return repos.jobRuns
    .where((r) => r.status.in(["failed", "timedOut", "abandoned", "interrupted"]).and(r.startedAt.gt(since)))
    .orderByDescending((r) => r.startedAt)
    .take(50)
    .toArray();
};

export default handler;
```

## Running a job on demand

### From the CLI

`job run <name>` loads the config, connects to the database and runs the job in the CLI process, as a run with `trigger: "manual"`. It is recorded, and retried, like a scheduled run. After the job's log lines it prints the outcome, and it exits with 0 only on `success`:

```bash
bun run quickservicets job run cleanup/expired-sessions
```

```text

{"level":"info","timestamp":"2026-10-19T15:36:59.621Z","message":"Expired sessions deleted","deleted":2,"job":"cleanup/expired-sessions","runId":"01a154cf-13dd-772d-a1d7-0d7aef5a641f"}
{"level":"info","timestamp":"2026-10-19T15:36:59.628Z","message":"job.finished","job":"cleanup/expired-sessions","runId":"01a154cf-13dd-772d-a1d7-0d7aef5a641f","status":"success","durationMs":8}
```

### From an endpoint or a hook

Endpoints and hooks get `req.jobs.run(name, options?)`. It records a run with `trigger: "code"` and resolves with its id as soon as the record is stored, without waiting for the job, which runs in the background with the same rules as a scheduled run:

```ts title="endpoints/exchange-rates/refresh/post.ts"
import type { Endpoint } from "@quickservicets/core";

/**
 * @summary Refresh the exchange rates now
 * @status 202
 */
const handler: Endpoint<unknown, { runId: string }> = (_repos, req) => req.jobs.run("sync/exchange-rates");

export default handler;
```

```bash
curl -i -X POST localhost:3000/exchange-rates/refresh
```

```txt
HTTP/1.1 202 Accepted

{"runId":"01a154cf-13fc-7551-b24f-4d39f0a1db0d"}
```

The name is checked against the job registry, so a typo fails the type check:

```ts
req.jobs.run("sync/exchange-rate");
// Argument of type '"sync/exchange-rate"' is not assignable to parameter of type 'JobName'.
```

The [Scheduled cleanup](/recipes/scheduled-cleanup/) recipe puts this together: a nightly job, an admin endpoint that triggers it, and one that reports how the run went.

## Overlapping runs

A run time can come while the previous run of the job is still going. With the default `overlap: "skip"`, the new run is recorded as `skipped` (with a zero duration) and the closure does not run. With `overlap: "parallel"`, it runs anyway, alongside the other one.

This job runs every second but takes 2.5 seconds:

```ts title="jobs/reports/slow.ts"
import { job } from "@quickservicets/core";

/** Takes 2.5 seconds, longer than its interval. */
export default job({ every: "1s" }, async () => {
  await Bun.sleep(2500);
  return { rows: 42 };
});
```

Runs on demand follow the same rule. While the server runs it, `job run` records a `skipped` run, prints a hint and exits with 1:

```bash
bun run quickservicets job run reports/slow
```

```text
Job reports/slow is already running; use --force to run it anyway
```

`--force` runs the job anyway, and `req.jobs.run(name, { force: true })` is the same from code. The runs show the two run times skipped while each run was going, and the manual one:

```bash
bun run quickservicets job runs reports/slow --limit 6
```

```text
ATTEMPT  TRIGGER   STATUS   STARTED                   DURATION
1        schedule  skipped  2026-10-19T15:38:18.014Z  0ms
1        schedule  skipped  2026-10-19T15:38:17.004Z  0ms
```

## Timeouts

A run may last at most its `timeout` (default `jobs.timeout`, 5 minutes). When it lasts longer, the run is recorded as `timedOut` with `error.message` `Timed out after <timeout>`, right away, without waiting for the closure, and `ctx.signal` is aborted with a `TimeoutError`. Whatever the closure does afterwards no longer changes the record. The slow report above, with `{ timeout: "1s" }` as its options:

```bash
bun run quickservicets job run reports/slow
```

```text
{"level":"info","timestamp":"2026-10-19T15:37:54.837Z","message":"job.started","job":"reports/slow","runId":"01a154cf-eb91-778c-96b2-acd676891aaf","status":"running"}
{"level":"error","timestamp":"2026-10-19T15:37:55.848Z","message":"job.finished","job":"reports/slow","runId":"01a154cf-eb91-778c-96b2-acd676891aaf","status":"timedOut","durationMs":1014}
Job reports/slow: timedOut in 1014ms
Error: Timed out after 1s
```

JavaScript cannot stop a function from the outside, so pass `ctx.signal` on to what accepts one, like `fetch`, and check it between steps of a long loop (`signal.throwIfAborted()`), so a timed-out run stops working too:

```ts title="jobs/sync/exchange-rates.ts"
import { job } from "@quickservicets/core";

type Rates = { rates: Record<string, number> };

export default job(
  { every: "1h" },
  async ({ repos, signal, log, run }) => {
    const response = await fetch("https://rates.example.com/latest?base=USD", { signal });
    if (!response.ok) throw new Error(`Rates service answered ${response.status}`);
    const { rates } = (await response.json()) as Rates;
    for (const [currency, rate] of Object.entries(rates)) {
      signal.throwIfAborted();
      await repos.exchangeRates.create({ currency, rate });
    }
    log.info("Rates stored", { currencies: Object.keys(rates).length, attempt: run.attempt });
    return { currencies: Object.keys(rates).length };
  },
  { timeout: "30s", retries: 3, retryDelay: "1m" },
);
```

## Retries

When a run ends as `failed`, `timedOut` or `abandoned`, and its `attempt` is at most `retries`, the job runs again after a delay that doubles each time: `retryDelay × 2^(attempt − 1)`. Each attempt is a new record with the same `job`, `trigger` and `scheduledAt` and the next `attempt`, and `ctx.run.attempt` tells the closure which one it is. With `retries: 3` and `retryDelay: "1m"`:

| Attempt | Starts |
| --- | --- |
| 1 | at the run time |
| 2 | 1 minute after attempt 1 ends |
| 3 | 2 minutes after attempt 2 ends |
| 4 | 4 minutes after attempt 3 ends, the last one |

`skipped`, `success` and `interrupted` runs are never retried. Retries apply to every run, scheduled or on demand. Here the rates service failed twice and then answered, and `job run` waited for the attempts and reported the last one:

```bash
bun run quickservicets job run sync/exchange-rates
```

The instance that recorded an attempt's outcome waits for the delay and then claims the next attempt through the run records, like any other run: with several instances it still runs once, and with `overlap: "skip"` a retry that comes while another run of the job is going is recorded as `skipped`. The wait is kept in memory, so an instance that stops before the delay ends drops that retry.

## Abandoned runs

An instance can die in the middle of a run, from a crash, an out-of-memory kill or a lost machine, leaving its record `running` forever. To notice, the instance running a job updates the record's `heartbeatAt` every third of the run's timeout, at most every 30 seconds and at least every second: every 30 seconds with the default 5-minute timeout, every 10 seconds with `timeout: "30s"`.

Every instance with jobs enabled checks, at startup and then once a minute, for `running` records whose last heartbeat (or start, without one) is older than their job's timeout. It marks them `abandoned`, with `finishedAt` and `error.message` `No heartbeat for <timeout>`. The update only applies to records that are still `running`, so when two instances check at the same time, only one marks a record and only that one retries it, following the job's `retries`.

An `abandoned` run no longer counts as running, so it does not hold back the next run of a job with `overlap: "skip"`.

Here an instance was killed (`kill -9`) one second into a run of a job with `{ timeout: "5s", retries: 1, retryDelay: "1s" }`. Seven seconds later another instance started, marked the run `abandoned` with `No heartbeat for 5s`, and ran the second attempt a second after that:

```bash
bun run quickservicets job runs reports/fragile
```

```text

2        schedule  success    2026-10-19T15:43:09.236Z  3005ms
```

## Shutdown

When the server gets `SIGTERM` or `SIGINT` (`Ctrl+C`, a container stop, a deploy), it stops scheduling and claiming runs, drops the retries it was waiting for, aborts the `ctx.signal` of its running jobs and waits up to `jobs.shutdownGrace` (default 10 seconds) for them. A job that stops on the signal records its own outcome: a closure that throws the abort reason ends as `failed`, with `Interrupted by shutdown` as its message. The runs still going when the grace ends are recorded as `interrupted`, with `error.message` `Interrupted by shutdown`, and then the process exits with 0. Neither is retried; the next run time runs as usual, on whichever instance is up.

Here `SIGTERM` came at 15:41:29, four seconds into two runs: `reports/polite` checks `signal.throwIfAborted()` in its loop and stopped at once, while `reports/stubborn` ignores the signal and was recorded as `interrupted` when the grace ended, ten seconds later:

```bash
bun run quickservicets job runs reports/polite --limit 1
bun run quickservicets job runs reports/stubborn --limit 1
```

```text
ATTEMPT  TRIGGER   STATUS   STARTED                   DURATION
1        schedule  failed   2026-10-19T15:41:25.007Z  4282ms
ATTEMPT  TRIGGER   STATUS       STARTED                   DURATION
1        schedule  interrupted  2026-10-19T15:41:25.011Z  14238ms
```

`dev` stops the server the same way on each reload, so a reload while a job is running waits up to `jobs.shutdownGrace`.

Set `jobs.shutdownGrace` below your platform's own stop timeout (Kubernetes waits 30 seconds by default before it kills a pod), so the runs are recorded before the process is killed.

## Retention

Run records are deleted after their job's `retention` (default `jobs.retention`, 30 days). Every instance with jobs enabled cleans up at startup and then once an hour, deleting the finished records whose `startedAt` is older than that; `running` records are kept, whatever their age. Records of a job you removed from `jobs/` use `jobs.retention`. Each cleanup logs how many records it deleted:

```json
{"level":"info","timestamp":"2026-10-19T15:31:41.665Z","message":"job-runs.cleanup","deleted":0}
```

Several instances can clean up at the same time: each record is deleted once.

## Several instances

Every instance of the service runs the scheduler, and they agree on who runs what through the run records. At a run time, each instance tries to insert the record for that job, run time and attempt; the unique index on the three lets one insert succeed, and only that instance runs the job. The others do nothing. So a job runs once per run time whatever the number of replicas, provided they share the database (on SQLite, the same database file).

To keep jobs off some instances, for example the ones that serve traffic, start them with `JOBS_ENABLED=false`. They neither schedule jobs nor check for abandoned runs nor clean up, but `req.jobs.run` still works there: the run happens on the instance that asked for it.
