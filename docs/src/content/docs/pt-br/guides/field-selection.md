Três camadas decidem quais campos uma resposta traz:

1. **A entidade** esconde campos com [`@hidden`](/pt-br/reference/tags/#hidden) e limita as respostas de listagem e leitura com [`@fields`](/pt-br/reference/tags/#fields).
2. **O cliente** reduz ainda mais as respostas de listagem e leitura com `?fields=` e `?exclude=`.
3. **Um endpoint customizado** molda o próprio resultado com as tags de endpoint [`@fields`](/pt-br/reference/tags/#fields-1) e [`@exclude`](/pt-br/reference/tags/#exclude).

Todas usam a mesma sintaxe de caminhos: nomes de campos separados por vírgulas, com pontos para propriedades aninhadas (`name,address.city`). Um caminho que passa por um array de objetos vale para cada item (`orders.total`), e manter um caminho mantém tudo o que está abaixo dele.

Os exemplos desta página usam esta entidade:

```ts check title="entities/User.ts"
/** @fields:list id,name,email */
export type User = {
  name: string;
  email: string;
  /** @hidden */
  passwordHash: string;
  /** @hidden:list */
  bio?: string;
  address?: {
    city: string;
    /** @hidden */
    zip?: string;
  };
};
```

## Campos que nunca são devolvidos

`@hidden` tira um campo de **todas** as respostas: listagem, leitura e também as respostas de criação, substituição e atualização. Os clientes ainda podem escrevê-lo. Funciona também em propriedades aninhadas, como `address.zip` acima.

```bash
curl -X POST localhost:3000/users -d '{"name":"Ana","email":"ana@example.com","passwordHash":"s3cret","bio":"Hi!","address":{"city":"Rio","zip":"20000"}}'
```

```json
{
  "name": "Ana",
  "email": "ana@example.com",
  "bio": "Hi!",
  "address": { "city": "Rio" },
  "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
  "createdAt": "2026-10-16T22:25:35.305Z",
  "updatedAt": "2026-10-16T22:25:35.305Z"
}
```

Os repositórios também deixam os campos ocultos de fora, e é por isso que o tipo `User` gerado os marca como opcionais (um trecho de `.generated/types.ts`):

```ts check title=".generated/types.ts"
// Generated by quickservice build. Do not edit.
import type { Many, One, Repository } from "@quickservice/core";

export type User = {
  id: string;
  createdAt: Date;
  updatedAt: Date;
  name: string;
  email: string;
  passwordHash?: string | null;
  bio?: string | null;
  address?: {
    city: string;
    zip?: string | null;
  } | null;
};

export type UserCreate = {
  name: string;
  email: string;
  passwordHash: string;
  bio?: string | null;
  address?: {
    city: string;
    zip?: string | null;
  } | null;
};

export type UserUpdate = {
  name?: string;
  email?: string;
  passwordHash?: string;
  bio?: string | null;
  address?: {
    city: string;

  } | null;
};

export type UserReferences = Record<never, never>;

  interface Repositories extends GeneratedRepositories {}

```

Quando o seu código precisa de um valor oculto, passe `includeHidden: true` para `findById`, `findOne` ou `list`. Este endpoint confere uma senha com o hash gravado. Ele supõe que `passwordHash` guarda um hash feito com `Bun.password.hash`, por exemplo por um hook na criação, e não o valor de exemplo enviado acima:

```ts check title="endpoints/sessions/post.ts"
import { HttpError, type Endpoint } from "@quickservice/core";

type Login = { email: string; password: string };

/** @summary Check a password */
const handler: Endpoint<Login, { id: string; name: string }> = async (repos, req) => {
  const { email, password } = await req.json();
  const user = await repos.users.findOne([{ field: "email", op: "eq", value: email }], { includeHidden: true });
  if (!user || !(await Bun.password.verify(password, user.passwordHash ?? ""))) {
    throw new HttpError(401, "Wrong email or password");
  }
  return { id: user.id, name: user.name };
};

export default handler;
```

```bash
curl -X POST localhost:3000/sessions -d '{"email":"ana@example.com","password":"s3cret"}'
```

```json
{ "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f", "name": "Ana" }
```

## Campos ocultos na listagem ou na leitura

`@hidden:list` esconde um campo só na rota de listagem (`GET /users`), e `@hidden:read` só na rota de leitura (`GET /users/:id`). As respostas de escrita continuam com ele. Aqui `bio` é longo demais para listas, mas a rota de leitura o mostra:

```bash
curl localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f
```

```json
{
  "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
  "createdAt": "2026-10-16T22:25:35.305Z",
  "updatedAt": "2026-10-16T22:25:35.305Z",
  "name": "Ana",
  "email": "ana@example.com",
  "bio": "Hi!",
  "address": { "city": "Rio" }
}
```

## Os campos que uma entidade expõe

A tag de entidade `@fields` lista os únicos caminhos que as rotas de listagem e leitura devolvem. `@fields:list` vale para a rota de listagem, `@fields:read` para a de leitura, e um `@fields` sem escopo para as duas. Os caminhos ocultos naquela rota continuam sendo removidos, e o `id` só volta quando você o lista.

Com `@fields:list id,name,email`, as listas ficam enxutas, enquanto a rota de leitura acima mantém todos os campos que não são ocultos:

```bash
curl localhost:3000/users
```

```json
{
  "data": [{ "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f", "name": "Ana", "email": "ana@example.com" }],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

Listar em `@fields` um caminho oculto na mesma rota para o build:

```text
entities/Post.ts: entity Post exposes "body" in @fields but it is hidden on list
```

A rota de listagem também só aceita filtros e ordenação nos campos que expõe, para que os clientes não sondem campos que não podem ver:

```bash
curl "localhost:3000/users?where[bio][eq]=Hi!"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "where[bio][eq]", "message": "Field \"bio\" cannot be filtered" }]
  }
}
```

```bash
curl "localhost:3000/users?sort=bio"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "sort", "message": "Field \"bio\" cannot be sorted" }]
  }
}
```

## Escolhendo campos na requisição

As rotas de listagem e leitura aceitam dois parâmetros de consulta, descritos na [referência de parâmetros de consulta HTTP](/pt-br/reference/http/):

- `fields`: os caminhos a manter.
- `exclude`: os caminhos a remover.

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?fields=name,address.city"
```

```json
{ "name": "Ana", "address": { "city": "Rio" } }
```

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?exclude=bio,createdAt,updatedAt"
```

```json
{
  "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
  "name": "Ana",
  "email": "ana@example.com",
  "address": { "city": "Rio" }
}
```

Quando os dois vêm juntos, `fields` é aplicado primeiro e `exclude` depois remove caminhos dessa seleção:

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?fields=name,address&exclude=address.city"
```

```json
{ "name": "Ana", "address": {} }
```

Os clientes só escolhem entre os caminhos que a rota expõe. Selecionar um caminho oculto ou não exposto, excluir um caminho fora de `fields` ou enviar uma lista vazia falha com 400:

```bash
curl "localhost:3000/users?fields=passwordHash"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "fields", "message": "Unknown field: passwordHash" }]
  }
}
```

```bash
curl "localhost:3000/users/01a146d2-1449-7559-ac9d-ecd5239cb52f?fields=name&exclude=email"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "exclude", "message": "Field is not selected: email" }]
  }
}
```

```bash
curl "localhost:3000/users?fields="
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid query",
    "details": [{ "field": "fields", "message": "Must list at least one field" }]
  }
}
```

`?fields=` e `?exclude=` não restringem os filtros: `?where[name][eq]=Ana&fields=email` filtra por `name` e devolve só `email`.

## Endpoints customizados

Um endpoint customizado molda o resultado com uma de duas tags de endpoint: `@fields <caminhos>` mantém caminhos e `@exclude <caminhos>` os remove. Usar as duas no mesmo endpoint para o build. A projeção vale para cada item de `data` quando o resultado é `{ data: [...] }`, para cada item de um array e para o próprio resultado nos outros casos; objetos `Response` e resultados vazios ficam intactos. Ela roda antes dos pós-hooks, que recebem os dados já projetados.

Num endpoint próprio, os caminhos são aplicados como escritos, e caminhos que faltam no resultado são ignorados:

```ts check title="endpoints/reports/signups/get.ts"
/** @exclude internalNote */
export default () => [
  { day: "2026-10-01", signups: 12, internalNote: "campaign A" },
  { day: "2026-10-02", signups: 9, internalNote: "campaign B" },
];
```

```bash
curl localhost:3000/reports/signups
```

```json
[
  { "day": "2026-10-01", "signups": 12 },
  { "day": "2026-10-02", "signups": 9 }
]
```

Num endpoint que substitui uma rota gerada de listagem ou leitura, a tag **substitui** as regras `@fields` e `@hidden:list`/`@hidden:read` da entidade naquela rota, e o build confere os caminhos contra a entidade. Os campos `@hidden` continuam de fora, porque o repositório nunca os devolve:

```ts check title="endpoints/users/get.ts"
import type { Endpoint } from "@quickservice/core";

/** @exclude address.zip */
const handler: Endpoint = (repos) => repos.users.query().orderBy((user) => user.name).page({ limit: 20, offset: 0 });

export default handler;
```

```bash
curl localhost:3000/users
```

```json
{
  "data": [
    {
      "name": "Ana",
      "email": "ana@example.com",
      "bio": "Hi!",
      "address": { "city": "Rio" },
      "id": "01a146d2-1449-7559-ac9d-ecd5239cb52f",
      "createdAt": "2026-10-16T22:25:35.305Z",
      "updatedAt": "2026-10-16T22:25:35.305Z"
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

Uma substituição sem nenhuma das tags mantém as regras da entidade naquela rota. Endpoints customizados ignoram `?fields=` e `?exclude=`, que só funcionam nas rotas geradas.

## Na documentação da API

O documento OpenAPI segue essas regras. Quando uma rota expõe menos campos que o registro completo, a resposta dela usa um schema reduzido, `UserListItem` na rota de listagem ou `UserRead` na de leitura, e os parâmetros `fields` e `exclude` listam os caminhos que os clientes podem escolher.
