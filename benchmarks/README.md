# Benchmarks

A performance study of a service generated by QuickService against equivalent hand-written services (Node with Express and Fastify, plain Bun, Python FastAPI, Go, Rust, .NET, Java, PHP and C++), all on PostgreSQL, with the same API, the same schema, the same data and the same load.

| Path | What it is |
| --- | --- |
| [`CONTRACT.md`](CONTRACT.md) | The API every stack implements, the schema, and the rules for implementers |
| [`quickservice/`](quickservice/) | The QuickService service (entities, two custom endpoints, migrations, Dockerfile) |
| [`schema/schema.sql`](schema/schema.sql) | The DDL of the QuickService migrations, shared by every stack |
| [`seed/`](seed/) | The deterministic dataset: 10,000 users, 1,000 organizations with 10 members each |
| [`conformance/conformance.ts`](conformance/conformance.ts) | Checks any base URL against the contract |
| [`load/`](load/) | The k6 scenarios |
| [`docker-compose.yml`](docker-compose.yml) | PostgreSQL 17.11 (2 CPUs, data directory in a 3 GB tmpfs, `synchronous_commit=off`) on the `qsbench` network |
| [`run.ts`](run.ts) | Builds, starts and measures one stack or all of them |
| `stacks/<name>/` | The hand-written services, one folder each with a `Dockerfile` |
| [`results/`](results/) | One JSON file per stack |

## Requirements

- Docker with at least 8 CPUs available (the service gets 2, PostgreSQL 2, k6 4).
- Bun 1.4.2, and `bun install` at the repository root.

Nothing else is needed on the host: PostgreSQL, k6 and the services run in containers. The runner uses host ports `55432` (PostgreSQL) and `18080` (the service under test), and only creates and removes containers and volumes whose names start with `qsbench-`.

## Running

From the repository root:

```bash
bun benchmarks/run.ts quickservice              # one stack
bun benchmarks/run.ts quickservice go rust      # several
bun benchmarks/run.ts quickservice-workers      # QuickService with server.workers = 2 (quickservice/Dockerfile.workers)
bun benchmarks/run.ts all                       # quickservice, quickservice-workers and every benchmarks/stacks/<name>
bun benchmarks/run.ts go --scenarios crud,query --duration 10s --warmup 5s
```

| Option | Default | Effect |
| --- | --- | --- |
| `--scenarios a,b` | all | Scenarios to run, by name (see below) |
| `--duration` | `30s` | Measured time per scenario |
| `--warmup` | `10s` | Warmup per scenario, discarded |
| `--vus` | `64` | Concurrent k6 virtual users |
| `--startup-runs` | `3` | Cold starts for the startup measurement |
| `--skip-build` | off | Reuse the existing `qsbench-<stack>` image |
| `--keep-going` | off | Run the load even when conformance fails |

For each stack, `run.ts`:

1. starts PostgreSQL with `docker compose` (left running between stacks; `docker compose -f benchmarks/docker-compose.yml down` removes it);
2. builds `qsbench-<stack>` from `stacks/<stack>/Dockerfile` (QuickService: `quickservice/Dockerfile`, or `quickservice/Dockerfile.<variant>` for `quickservice-<variant>`, with the repository root as context) and records the image size;
3. drops and recreates the schema from `schema/schema.sql` and loads the seed;
4. creates the container with `--cpus=2 --memory=1g`, the environment from the contract and a fresh upload volume, then measures startup: `docker start` to the first `200` on `GET /health`, polled every 5 ms, over 3 cold starts (median reported; this includes Docker's own start overhead, the same for every stack);
5. samples `docker stats` from then on: idle memory over 5 seconds, then memory and CPU per scenario;
6. runs the conformance test, and stops there if it fails;
7. starts a small janitor container that deletes stored uploads older than a few seconds (a 30-second upload run would otherwise write gigabytes), then, for each scenario, reloads the seed, runs k6 for the warmup, then for the measured run;
8. writes `results/<stack>.json` and removes the container and its volume.

## Scenarios

k6 (`grafana/k6:2.3.0`) runs in a container on the same network with 4 CPUs, 64 VUs, no think time, keep-alive connections. Each request is tagged, so the results have totals and per-endpoint numbers. An error is any status other than the expected one.

| Name | Requests per iteration |
| --- | --- |
| `crud` | `GET /users/{random seeded id}`, `GET /users?limit=20&offset={random}`, `POST /users`, `PATCH /users/{new id}`, `DELETE /users/{new id}` |
| `query` | `GET /users?where[role][eq]=admin&where[age][gte]=30&sort=-age,email&fields=email,name&limit=20`, `GET /organizations?populate=members&limit=10` |
| `custom` | `GET /organizations/{random seeded id}/stats` |
| `upload` | `POST /media`, multipart, a 51,288-byte PNG |
| `health` | `GET /health` (the framework's floor) |
| `get_user`, `list_users`, `create_user`, `filter_users`, `populate_orgs` | one request of the above, alone |

## After the optimizations

The profile in [`analysis/quickservice-profile.md`](analysis/quickservice-profile.md) led to twelve framework changes (single-statement writes and deletes, projection without deep clones, buffered request logging, counting only when the total is read, `server.workers`, precompiled SQL, reference arrays in the row SELECT, fluent `aggregate()`, single-pass multipart and smaller per-request costs). Requests per second, better of two rounds, same setup as above; the stats endpoint now uses `aggregate()`. Raw numbers are in `results/before-optimizations/` and `results/after-optimizations/`. A second profile of the optimized service, with the opportunities that remain, is in [`analysis/quickservice-profile-2.md`](analysis/quickservice-profile-2.md).

## Results

`results/<stack>.json` holds the settings, the environment, the image size, the startup samples, idle and peak memory, the conformance counts and, per scenario, requests, req/s, latency (avg, p50, p90, p99, max in ms), error rate, average and peak CPU and memory, and the same numbers per endpoint. The raw k6 summaries stay in `benchmarks/.cache/out/<stack>/`.

## Working on a stack

Start PostgreSQL and load the schema and seed, then run the service on the host against `localhost:55432` and check it:

```bash
docker compose -f benchmarks/docker-compose.yml up -d --wait
(echo 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'; cat benchmarks/schema/schema.sql; bun benchmarks/seed/seed.ts) \
  | docker exec -i qsbench-postgres psql -q -U bench -d bench -v ON_ERROR_STOP=1
# start your service on port 8080, then:
BASE_URL=http://localhost:8080 bun test ./benchmarks/conformance/conformance.ts
```

The conformance test needs a fresh seed: reload it (`bun benchmarks/seed/seed.ts | docker exec -i qsbench-postgres psql -q -U bench -d bench`) before each run. To run the QuickService service on the host:

```bash
cd benchmarks/quickservice
bun run build
NODE_ENV=production bun run start   # uses localhost:55432 unless DATABASE_URL is set
```

The schema comes from the QuickService migrations. After changing the entities, run `bun run quickservice migration add <Name>` in `benchmarks/quickservice`, then `bun benchmarks/schema/generate.ts`.
