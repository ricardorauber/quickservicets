The memory database forgets everything on each restart. In this page you move the project to PostgreSQL, create its tables with a **migration**, and raise the populate depth for the endpoint of the next part.

## Why migrations

A SQL database needs tables before it can store records. A migration is a TypeScript file in `migrations/` that changes the database from one version of your model to the next. quickservice writes it for you by comparing your entities with the last migration, and you review it before applying it.

## Start PostgreSQL

Any PostgreSQL server works. With Docker:

```bash
docker run -d --name identity-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:16
```

## Point the project at it

Stop the dev server first (`Ctrl+C`). Then put the connection URL in the project's `.env`, which Bun loads for every command:

```bash
DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres
```

And switch the adapter in `quickservice.config.ts`:

```ts check
import { defineConfig, postgresAdapter } from "@quickservice/core";

export default defineConfig({
  database: postgresAdapter({ url: process.env.DATABASE_URL! }),
});
```

:::note
`.env` is in the project's `.gitignore`, so the credentials stay out of git.
:::

## Create the first migration

```bash
bun run quickservice migration add Initial
```

```text
Created migrations/20261016222539_Initial.ts
```

The name is in PascalCase: an uppercase letter, then letters and digits. The command also writes a snapshot of the model to `migrations/meta/`, which the next migration compares against. Open the file to review it. Here it is, shortened:

```ts check title="migrations/20261016222539_Initial.ts"
// Generated by quickservice migration add. Review and edit as needed.
// ctx.repos reflects the latest model, not the model at the time of this migration.
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql("CREATE TABLE \"memberships\" (\n\t\"id\" text PRIMARY KEY NOT NULL,\n\t\"created_at\" timestamp with time zone NOT NULL,\n\t\"updated_at\" timestamp with time zone NOT NULL,\n\t\"organization\" text NOT NULL,\n\t\"user\" text NOT NULL,\n\t\"active\" boolean NOT NULL\n);");
  await ctx.sql("CREATE TABLE \"permissions\" (\n\t\"id\" text PRIMARY KEY NOT NULL,\n\t\"created_at\" timestamp with time zone NOT NULL,\n\t\"updated_at\" timestamp with time zone NOT NULL,\n\t\"module\" text NOT NULL,\n\t\"action\" text NOT NULL,\n\tCONSTRAINT \"permissions_action_check\" CHECK (\"permissions\".\"action\" in ('manage', 'view'))\n);");
  // … the other tables, foreign keys and indexes
}

export async function down(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("DROP TABLE \"memberships\" CASCADE;");
  // … the other tables
}
```

The migration creates:

- One table per entity, plus `files` and `media` for the built-in file entities.
- One junction table per one-way reference array: `memberships__profiles`, `organizations__modules`, `profiles__permissions` and `teams__profiles`.
- One junction table for the N-N relation between teams and users: `teams__users`.

Derived sides get nothing: `users` has no `memberships` column, because each membership stores its `user`. Enum fields become text columns with a `CHECK` on their values, like `action` above.

## Apply it

List the migrations first:

```bash
bun run quickservice migration list
```

```text
20261016222539_Initial  pending
```

Apply every pending migration:

```bash
bun run quickservice migrate
```

```text
Applied 20261016222539_Initial
```

Now the list shows it as applied, and running `migrate` again changes nothing:

```bash
bun run quickservice migration list
bun run quickservice migrate
```

```text
20261016222539_Initial  applied
Database is up to date (0 migrations applied)
```

## Run on PostgreSQL

Start the dev server again:

```bash
bun run dev
```

The routes are the same as before. Only the storage changed, and records now survive restarts:

```bash
curl -X POST localhost:3000/modules -d '{"slug":"billing","active":true}'
```

## Allow deeper populate paths

The next part checks a user's permissions by loading each membership's profiles, their permissions and each permission's module in one go: `profiles.permissions.module`. That path has three segments, and populate allows two by default. After you recreate a few records (module, permission, profile, organization, user and membership), try it:

```bash
curl "localhost:3000/memberships/<membership-id>?populate=profiles.permissions.module"
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Populate depth exceeds 2",
    "details": [{ "field": "populate", "message": "Populate depth exceeds 2" }]
  }
}
```

Raise the limit with `populate.maxDepth`. This is the finished `quickservice.config.ts`:

```ts check title="quickservice.config.ts"
import { defineConfig, postgresAdapter } from "@quickservice/core";

export default defineConfig({
  database: postgresAdapter({ url: process.env.DATABASE_URL! }),
  // "profiles.permissions.module" has three segments.
  populate: { maxDepth: 3 },
});
```

The dev server restarts when the config changes. The same request now returns the whole chain:

```bash
curl "localhost:3000/memberships/<membership-id>?populate=profiles.permissions.module"
```

## When the model changes later

While `bun run dev` runs on PostgreSQL, it creates a migration for you whenever an entity change needs one, names it after the change, and prints `Created migrations/<id>_<Name>.ts. Run "quickservice migrate" to apply it.` Review the file, then run `migrate`.

- To write migrations only by hand, set `migrations: { autoInDev: false }` in the config and run `migration add <Name>` yourself.
- `bun run quickservice migration remove` deletes the latest migration while it is not applied yet.
- `bun run quickservice migrate <name or id>` migrates up or down to that migration, and `migrate 0` reverts them all.
