A service reads two kinds of environment variables: the ones your code needs, like a database URL or an API key, which you declare in the config with a type, and the `QS_*` variables, which set any config key or feature option without editing the config. Both are checked when the service starts, so a missing or wrong value stops it with one clear message instead of failing later.

## Declaring variables with `env`

The `env` key lists the variables the service needs, each with an option schema: the same `string()`, `integer()`, `url()`, `secret()` and friends that feature options use.

```ts check title="quickservice.config.ts"
import { defineConfig, integer, oneOf, postgresAdapter, secret, url } from "@quickservice/core";

export default defineConfig({
  database: postgresAdapter({ url: process.env.DATABASE_URL! }),
  env: {
    DATABASE_URL: url().describe("The PostgreSQL connection URL."),
    STRIPE_KEY: secret().describe("The Stripe secret key."),
    REPORT_HOUR: integer().min(0).max(23).default(6),
    LOG_FORMAT: oneOf(["json", "text"]).optional(),
  },
});
```

A variable is required unless it has a default or is `optional()`. Names use upper snake case (`^[A-Z][A-Z0-9_]*$`), and `QS_*` names are reserved for the overrides below.

## Startup validation

When the service starts (and when `quickservice build` loads the config), every declared variable is read and parsed. All the problems are reported together, and the service does not start:

```text
Invalid environment:
  DATABASE_URL is required (url)
  REPORT_HOUR: expected an integer of at most 23, got "25"
```

Values are parsed from text the way their schema says: numbers, `true`/`false`/`1`/`0` for booleans, and lists as comma-separated items or a JSON array.

## Reading variables with `env`

`env` holds the parsed values, typed from the declarations: `quickservice build` writes their types into `.generated/types.ts`, so `env.REPORT_HOUR` is a `number` and `env.LOG_FORMAT` is `"json" | "text" | undefined`.

<details>
<summary>The part of <code>.generated/types.ts</code> these declarations produce</summary>

```ts check title=".generated/types.ts"
// Generated by quickservice build (shortened).
declare module "@quickservice/core" {
  interface EnvVars {
    DATABASE_URL: string;
    STRIPE_KEY: string;
    REPORT_HOUR: number;
    LOG_FORMAT: "json" | "text" | undefined;
  }
}
export {};
```

</details>

Read them anywhere in your code, once the config has been resolved:

```ts check title="jobs/report.ts"
import { env, job } from "@quickservice/core";

export default job("0 * * * *", async () => {
  if (new Date().getUTCHours() !== env.REPORT_HOUR) return "not now";
  return env.LOG_FORMAT === "text" ? "report sent" : { sent: true };
});
```

Features declare their own variables with the `env` field of `defineFeature`; they are checked and read the same way, together with the project's.

## `.env.example`

`quickservice build` writes `.env.example` with one commented block per declared variable: its description, type, default (or `required`) and the feature that declared it. Secrets and variables without a default are left empty:

```bash
# Generated by quickservice build from quickservice.config.ts. Do not edit.

# The PostgreSQL connection URL.
# Type: url
# required
DATABASE_URL=

# The Stripe secret key.
# Type: secret
# required
STRIPE_KEY=

# Type: integer
# default: 6
REPORT_HOUR=6
```

Commit it, so anyone setting up the service knows what to provide. A hand-written `.env.example` (one without the header line) is never overwritten; the build prints a warning instead.

## `quickservice env check`

`quickservice env check` checks the environment the service would start with: the process's variables and the `.env` files Bun loads (`.env`, then `.env.<NODE_ENV>`, then `.env.local`). It prints one line per declared variable, then the `QS_*` overrides that are set, and exits with 1 when a variable is missing or invalid:

```bash
bun run quickservice env check
```

```text
DATABASE_URL ok postgres://localhost:5432/app
STRIPE_KEY ok [secret]
REPORT_HOUR default 6
QS_SERVER_PORT sets server.port = 4000
```

Run it in a deploy pipeline before starting the new version.

## Secrets and masking

A `secret()` value never appears in what the framework prints or writes: `env check`, error messages, logs of the resolved config and `.env.example` show `[secret]` instead, and so does printing `env` or a feature's options. Secrets have no defaults, so they are always provided by the environment.

## Overriding config keys with `QS_*`

Every config key that holds a value can be set by a variable named `QS_` plus its path in upper snake case, which wins over the config file:

| Config key | Variable |
| --- | --- |
| `server.port` | `QS_SERVER_PORT` |
| `server.workers` | `QS_SERVER_WORKERS` |
| `jobs.retries` | `QS_JOBS_RETRIES` |
| `jobs.limits.logLines` | `QS_JOBS_LIMITS_LOG_LINES` |
| `lifecycle.startTimeout` | `QS_LIFECYCLE_START_TIMEOUT` |

A feature's options follow the same rule under its key: the `text` option of a `greeting` feature is `QS_GREETING_TEXT`, and a nested `limits.max` option is `QS_GREETING_LIMITS_MAX`. Keys that hold code (`database`, `logger`, `storage`, `middleware`, `env`, `docs.openapi`) have no variable. The [configuration reference](/reference/config/) lists every variable.

Two kinds of options have more than one variable:

- A switchable section, declared with `toggle({...})`, takes `true`, `false` or an object in the config. `QS_<PATH>` sets the whole section from `true`, `false`, `1`, `0` or JSON, then `QS_<PATH>_ENABLED` and the variables of its keys apply on top: `QS_SECURITY_CORS=false` turns a `security.cors` section off, and `QS_SECURITY_CORS_ENABLED=true` set as well turns it back on.
- A map of named entries, declared with `record(...)`, gets variables for the entries written in the config, with the entry name in upper case and hyphens as underscores: the `url` of a `billing` entry of `http.services` is `QS_HTTP_SERVICES_BILLING_URL`. `QS_<PATH>` sets the whole map from JSON first (`QS_HTTP_SERVICES='{"crm":{"url":"https://c.dev"}}'`).

Rates (`rate()`) are written `<count>/<window>`, like `100/min` or `5/10s`, and IP options (`cidr()`) take an address, a block like `10.0.0.0/8` or the names `loopback`, `private` and `linklocal`; a list of them is comma-separated (`10.0.0.0/8, loopback`).

A `QS_*` variable that matches no key is not an error, since environments are often shared: the server logs it once at startup, and `build` and `env check` print a warning with the closest name.

## Turning features on and off with `QS_<KEY>_ENABLED`

`QS_<KEY>_ENABLED=true` turns a feature on without a key in the config, with its default options, and `QS_<KEY>_ENABLED=false` turns it off even when the config enables it:

```bash
QS_GREETING_ENABLED=false bun .generated/server.ts
```

A feature turned off at startup serves none of its routes and runs none of its jobs.

## Legacy variables

A few variables predate the `QS_*` names and still work: `PORT` (`server.port`), `QS_WORKERS` (`server.workers`), `DATABASE_SCHEMA` (`schema`), `FILES_SIGNING_SECRET` (`files.signingSecret`), `JOBS_ENABLED` (`jobs.enabled`) and `NODE_ENV=production` (`production`). A `QS_*` variable wins over its legacy name.

## Precedence

For each config key and feature option, the first of these that is set wins:

1. a feature tag on the entity, field or route (for feature options, see [Project features](/guides/project-features/#tags));
2. the `QS_*` variable;
3. the legacy variable;
4. the value in `quickservice.config.ts`;
5. the default.
