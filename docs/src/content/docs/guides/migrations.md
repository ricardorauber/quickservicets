Your entities describe what the database should look like; migrations are the steps that take a database there. Each migration is a TypeScript file with an `up` function that applies a change and a `down` function that undoes it. The CLI writes them for you from model changes, and you can edit them or write your own.

Migrations work with SQLite, PostgreSQL and MongoDB. The in-memory adapter keeps no schema, so `migrate` has nothing to do there and `migration add` fails with `Migrations are not used with the memory adapter`.

Run the commands inside the project with `bun run quickservice <command>`. The examples on this page use a SQLite project with this entity:

```ts check title="entities/User.ts"
export type User = {
  /** @unique */
  email: string;
};
```

## `migration add`

`migration add <Name>` compares the entities with the last migration's snapshot and writes the difference:

```bash
bun run quickservice migration add Initial
```

```text
Created migrations/20261016223225_Initial.ts
```

The name must be PascalCase (`^[A-Z][A-Za-z0-9]*$`) and unique; the file is `migrations/<YYYYMMDDHHmmss>_<Name>.ts`. Now add a field to `User` in `entities/User.ts`:

```ts check
export type User = {
  /** @unique */
  email: string;
  age?: number;
};
```

`build` (and so `dev`) notices the change:

```bash
bun run quickservice build
```

```text
Built 3 entities, 0 custom endpoints and 0 hooks.
Warning: Model has changes without a migration. Run "quickservice migration add <Name>"
```

(The three entities are `User` and the built-in `File` and `Media`.) Add a migration for it:

```bash
bun run quickservice migration add AddAge
```

```text
Created migrations/20261016223226_AddAge.ts
```

The generated file:

```ts check title="migrations/20261016223226_AddAge.ts"
// Generated by quickservice migration add. Review and edit as needed.
// ctx.repos reflects the latest model, not the model at the time of this migration.
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql("ALTER TABLE `{{default_schema}}users` ADD `age` real;");
}

export async function down(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("ALTER TABLE `{{default_schema}}users` DROP COLUMN `age`;");
}
```

- Statements that can lose data (dropping a table or column, changing a column type) get a `// WARNING: possible data loss` comment. Read them before applying.
- On SQLite, `{{default_schema}}` stands for the [default schema](/guides/configuration/#environment-variables) prefix. `migrate` replaces it when it runs, so one migration works with any `DATABASE_SCHEMA`. On PostgreSQL, default-schema tables are left unqualified and the search path picks the schema.
- A name that is taken, or not PascalCase, fails:

```bash
bun run quickservice migration add AddAge
bun run quickservice migration add addAge
```

```text
A migration named AddAge already exists: 20261016223226_AddAge
Migration names must be PascalCase and match ^[A-Z][A-Za-z0-9]*$ (got "addAge")
```

### Snapshots

Next to each migration, `migration add` saves the model it produces in `migrations/meta/<id>.snapshot.json`. The next `migration add` diffs against the latest snapshot on disk, not against the database, so commit the snapshots with the migrations and do not edit them.

### Data migrations

When nothing changed in the model, `migration add` still creates a file, with empty `up` and `down`, for changes you write by hand:

```bash
bun run quickservice migration add BackfillAges
```

```text
Created migrations/20261016223248_BackfillAges.ts
```

`up` and `down` receive a `MigrationContext`:

- `ctx.sql` runs SQL on the migration connection, as a string or as a tagged template whose values are bound as parameters;
- `ctx.db` is the Drizzle database instance of that connection;
- `ctx.repos` holds the repositories of the current model. They follow the latest entities, not the model at the time of the migration, so prefer `ctx.sql` in migrations that must keep working after later changes.

```ts check title="migrations/20261016223248_BackfillAges.ts"
import type { MigrationContext } from "@quickservice/core";

const DEFAULT_AGE = 18;

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql`update users set age = ${DEFAULT_AGE} where age is null`;
}

export async function down(ctx: MigrationContext): Promise<void> {
  await ctx.sql`update users set age = null where age = ${DEFAULT_AGE}`;
}
```

### Automatic migrations in `dev`

While `quickservice dev` runs, a model change creates a migration named after it, such as `AddAgeToUsers`, `CreateOrder`, `RemoveAgeFromUsers` or `UpdateModel` when several entities change. It prints `Created migrations/<id>.ts. Run "quickservice migrate" to apply it.`; it never applies it for you. Turn this off with `migrations.autoInDev`; `dev` then prints the pending-changes warning instead:

```ts check title="quickservice.config.ts"
import { defineConfig, sqliteAdapter } from "@quickservice/core";

export default defineConfig({
  database: sqliteAdapter({ path: process.env.DATABASE_PATH! }),
  migrations: { autoInDev: false },
});
```

## `migrate`

`migrate` with no target applies every pending migration, in id order:

```bash
bun run quickservice migrate
```

```text
Applied 20261016223225_Initial
Applied 20261016223226_AddAge
```

Running it again changes nothing:

```text
Database is up to date (0 migrations applied)
```

Applied migrations are recorded in the `__quickservice_migrations` table. Each one runs in its own transaction together with its history row: when it fails, its changes roll back, the command stops with exit code 1 and names the migration, and the migrations before it stay applied.

### Migrating to a target

Give a target, by name or full id, to move forward or back to it. Going back runs `down` of every newer applied migration, newest first:

```bash
bun run quickservice migrate Initial
```

```text
Reverted 20261016223226_AddAge
```

```bash
bun run quickservice migrate AddAge
```

```text
Applied 20261016223226_AddAge
```

Target `0` reverts everything:

```bash
bun run quickservice migrate 0
```

```text
Reverted 20261016223226_AddAge
Reverted 20261016223225_Initial
```

An unknown target, or an applied migration whose file is gone, stops the command:

```text
Unknown migration target: Nope
```

### `--force` in production

In production (`NODE_ENV=production`, or `production: true` in the config), `migrate` refuses to revert anything without `--force`:

```bash
NODE_ENV=production bun run quickservice migrate Initial
```

```text
Reverting migrations in production requires --force (would revert: 20261016223226_AddAge)
```

```bash
NODE_ENV=production bun run quickservice migrate Initial --force
```

```text
Reverted 20261016223226_AddAge
```

## `migration list`

`migration list` shows every migration and its status:

```bash
bun run quickservice migration list
```

```text
20261016223225_Initial  applied
20261016223226_AddAge  pending
```

| Status | Meaning |
| --- | --- |
| `applied` | In the database's history. |
| `pending` | On disk, not applied yet. |
| `missing` | In the history, but its file is gone. |
| `unknown` | The database could not be reached; a warning says why. |

With no migrations at all, it prints `No migrations`.

## `migration remove`

`migration remove` deletes the newest migration and its snapshot, so you can change the model and add it again. It only removes a migration that is not applied:

```bash
bun run quickservice migration remove
```

```text
Migration 20261016223226_AddAge is applied. Revert it with "quickservice migrate Initial" first
```

After `migrate Initial`:

```bash
bun run quickservice migration remove
```

```text
Removed migrations/20261016223226_AddAge.ts
Removed migrations/meta/20261016223226_AddAge.snapshot.json
```

With nothing left, it fails with `No migrations to remove`.

## `migration script`

`migration script [from] [to]` prints the SQL between two points without running anything, for review or for a DBA to apply. `from` defaults to `0` (an empty database) and `to` to the newest migration; both take a name, a full id or `0`. From `Initial` to the newest:

```bash
bun run quickservice migration script Initial
```

```sql
-- 20261016223226_AddAge (up)
ALTER TABLE `users` ADD `age` real;
insert into __quickservice_migrations (id, name, applied_at) values ('20261016223226_AddAge', 'AddAge', cast(strftime('%s', 'now') as integer) * 1000);
```

When `to` comes before `from`, the script has the `down` SQL, newest first:

```bash
bun run quickservice migration script AddAge Initial
```

```sql
-- 20261016223226_AddAge (down)
ALTER TABLE `users` DROP COLUMN `age`;
delete from __quickservice_migrations where id = '20261016223226_AddAge';
```

Values bound in tagged templates are written inline. For the `BackfillAges` migration above:

```sql
-- 20261016223248_BackfillAges (up)
update users set age = 18 where age is null;
insert into __quickservice_migrations (id, name, applied_at) values ('20261016223248_BackfillAges', 'BackfillAges', cast(strftime('%s', 'now') as integer) * 1000);
```

The SQL is collected by running each migration with a `ctx.sql` that records statements. Code that uses `ctx.db` or `ctx.repos` cannot be recorded, so it shows up as `-- custom code in <id>, not scriptable`.

`--output <file>` writes the script to a file and prints nothing:

```bash
bun run quickservice migration script --output schema.sql
```

## Renames

Generated migrations never guess renames. Renaming a field or an entity becomes a drop followed by an add, which loses the data. Renaming `age` to `years` generates:

```ts check title="migrations/20261016223301_RenameAge.ts"
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("ALTER TABLE `{{default_schema}}users` DROP COLUMN `age`;");
  await ctx.sql("ALTER TABLE `{{default_schema}}users` ADD `years` real;");
}

export async function down(ctx: MigrationContext): Promise<void> {
  // WARNING: possible data loss
  await ctx.sql("ALTER TABLE `{{default_schema}}users` DROP COLUMN `years`;");
  await ctx.sql("ALTER TABLE `{{default_schema}}users` ADD `age` real;");
}
```

To keep the data, replace both bodies with a rename:

```ts check
import type { MigrationContext } from "@quickservice/core";

export async function up(ctx: MigrationContext): Promise<void> {
  await ctx.sql("ALTER TABLE `{{default_schema}}users` RENAME COLUMN `age` TO `years`;");
}

export async function down(ctx: MigrationContext): Promise<void> {
  await ctx.sql("ALTER TABLE `{{default_schema}}users` RENAME COLUMN `years` TO `age`;");
}
```

The snapshot already describes the new model, so the next `migration add` starts from there. One rename is detected: when a join table changes name (for example with a new `@joinTable`) but still links the same fields, the migration renames the table and keeps its rows.

## MongoDB

On MongoDB the same commands work, with these differences:

- Generated migrations create and drop indexes (for `@unique`, `@index` and the like); there are no tables to create.
- `ctx` is a `MongoMigrationContext`: `ctx.db()` is the native database of the default schema, `ctx.db("<schema>")` the one of another schema, `ctx.client` the `MongoClient`, and `ctx.repos` the repositories.
- History lives in the `_migrations` collection of the default database.
- Migrations run without transactions, because index changes cannot run inside one; `migrate` prints `Warning: MongoDB migrations run without transactions: index changes cannot run inside one`.
- Removing or renaming an entity never drops its collection. The generated `up` has `// TODO: data in collection <name> is kept; drop it here if intended` instead.
- `migration script` prints `mongosh` commands, such as `db.users.createIndex(...)`, and custom code as `// custom code in <id>, not scriptable`.

A hand-written data migration on MongoDB:

```ts check
import type { MongoMigrationContext } from "@quickservice/core";

export async function up(ctx: MongoMigrationContext): Promise<void> {
  await ctx.db().collection("users").updateMany({ age: null }, { $set: { age: 18 } });
}

export async function down(ctx: MongoMigrationContext): Promise<void> {
  await ctx.db().collection("users").updateMany({ age: 18 }, { $set: { age: null } });
}
```
